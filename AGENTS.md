# AGENTS.md: правила для агентов, разрабатывающих `frugal`

Проект: **Frugal SDD** (`frugal`), прототип экономии токенов в SDD-конвейере OpenSpec + opencode для кейса СберТеха.
Разработка ведётся через **Codex**, объём кода не ограничен. Цель — максимум баллов по критериям кейса: полнота, строгость замера и доказательность важнее скорости. План работ задаётся гейтами (`TZ.md` §16), а не сроками.

**Команда «делай».** Открой [стартовый промпт](docs/START_PROMPT.md) и [единую стратегию](STRATEGY.md). Как координатор, начни с WP-00. При повторном запуске сверь ветку, результаты тестов, артефакты и реестры, затем продолжи с первого незакрытого гейта. Сам распределяй пакеты, проверяй результаты и принимай обычные инженерные решения. Для изменений защищённых правил действуют разделы 1 и 9 этого файла.

> Этот файл читается агентом в каждом запросе. Держи его коротким: детали живут в `TZ.md`, а здесь только правила и ссылки.

## 1. Источники истины (по убыванию приоритета)

1. `case/token-efficient-sdd.pdf`: кейс. Из общей презентации `docs/source/hackathon-presentations.pdf` к нему относятся слайды 23–33.
2. `TZ.md`: техническое задание. Инварианты §2.2, правила качества §4.3, baseline §7, изоляция §10.1 **без согласования не менять**. `STRATEGY.md` объединяет планы, задаёт порядок автономной работы и объясняет выбор методов. Для реализации используй одну систему обозначений из ТЗ — `frugal`, WP-00…WP-16, E0…E10 и E-x.
3. Этот файл.
4. `RESEARCH.md` и `docs/research/*.md`: исследование Claude о OpenSpec, opencode, техниках и инструментах. `SPEC.md` — архив инженерных предложений Codex из GitHub, его источники сохранены в `reports/` и `research_notes/`. Внешние интерфейсы сверяй с фактически установленной версией.
5. `docs/HYPOTHESES.md`, `docs/DECISIONS.md`, `docs/EXPERIMENTS.md`: живые реестры.

Перед работой над пакетом `WP-xx` прочитай его описание в `TZ.md` §16.3 и разделы ТЗ, на которые оно ссылается.

## 2. Золотые правила (нарушение обнуляет баллы)

1. **Одна модель на A/B-пару.** Модель и провайдер одинаковы во всех вызовах base и opt. Удешевлять стадию другой моделью запрещено.
2. **Требования не урезаются, стадии не пропускаются.** proposal, specs, design, tasks, implement, review (≥ 1 итерация LLM), verify есть в обеих ветках.
3. **Baseline B0 заморожен** после первого калибровочного прогона: `assets/agents/base/`, `assets/commands/base/`. Любое изменение = новая версия B0 и перезапуск всех base-прогонов, с записью в `DECISIONS.md`.
4. **Эксперименты только в изоляции:** временная директория **вне** `хакатон/`, свежий клон демо-репо, отдельные каталоги конфигурации и данных opencode на прогон, skills OpenSpec только с `--scope project`. Никогда не запускай замерные прогоны opencode внутри дерева этого проекта: он подхватит этот AGENTS.md.
5. **Скрытые тесты** (`bench/features/*/hidden_tests/`) не попадают в рабочую копию агента до конца конвейера. При разработке промптов `frugal` не подгоняй их под содержимое скрытых тестов.
6. **Все цифры в отчёте берутся из `bench/runs/`**, их генерирует код. Ручной ввод чисел запрещён.
7. **Каждая оптимизация за флагом** (`frugal.yaml: flags.*`). В base все флаги выключены.
8. **Никакого кода под конкретный демо-репо** в `packages/`. Всё репо-специфичное хранится в `frugal.yaml` целевого репо.
9. **Сначала детерминированно.** Если шаг можно сделать без LLM (парсинг, трассировка, гейты, капсула, отметка задач), делай без LLM.
10. **Ничего не теряем.** Сжатый вывод всегда содержит путь к полному выводу на диске. Ошибки, assertion и предупреждения при сжатии никогда не выкидываются.
11. **Лицензии:** не встраиваем код под AGPL (DCP), ELv2 (context-mode), BUSL (RTK), Commons Clause. MIT и Apache-2.0 можно, с указанием источника.
12. **Секреты:** ключи только в переменных окружения или `.env` (в `.gitignore`). В манифесты, логи и отчёты ключи не пишутся.

## 3. Версии (закреплены, ставятся локально)

- opencode **V1** `opencode-ai@1.19.6` (плагин: `@opencode-ai/plugin`) для основных экспериментов. V2 (`@opencode/cli` 2.x) поддерживается обязательно: плагин экспортирует и V1 `server()`, и V2 `setup()`, на V2 идёт отдельный A/B (E10).
- OpenSpec `@fission-ai/openspec@2.1.1` с `--scope project` (запасной вариант `1.17.0`, см. `DECISIONS.md` ADR-001).
- Для ядра `frugal` действует нижняя граница Node ≥ 20. Для стенда используй Node ≥ 22.20.0 и записывай точную версию в манифест каждого прогона. Этого требует OpenSpec 2.1.1, для запасного OpenSpec 1.17.0 достаточно Node ≥ 22.12.0. Для анализа нужен Python ≥ 3.11 (uv).

Вызывай инструменты из `node_modules/.bin` проекта или через `npx --no-install`, а не глобальные установки.

## 5. Стек и конвенции

- **TypeScript:** ESM, `strict: true`, тесты на vitest, линт и формат через biome (или eslint + prettier, как решено в WP-00). Без тяжёлых зависимостей.
- **Python** (только `analysis/`): uv, pytest, ruff; pandas и matplotlib/plotly.
- Код, идентификаторы и комментарии на английском. Документация и отчёты на русском.
- Коммиты в стиле Conventional Commits: `feat(meter): ...`, `fix(plugin): ...`, `exp: E1 results`.
- Выводы инструментов `frugal` **детерминированы и отсортированы**: нестабильный вывод ломает кэш провайдера.
- Формат данных прогонов описан в `TZ.md` §10.2 (`calls.jsonl`) и §10.6 (`manifest.json`). Не меняй схему без ADR.

## 6. Команды

> Заполняется в WP-00 по мере появления. Пока это план.

```bash
npm install                 # зависимости монорепо
npm test                    # юнит-тесты TS
npm run build               # сборка CLI и плагина
uv run --project analysis pytest   # тесты анализа

npx frugal run --mode baseline  --feature add-transfer-limits --model <id> --runs 1 --dry-run
npx frugal run --mode optimized --feature add-transfer-limits --model <id> --runs 1
npx frugal run --experiment E3      # эксперимент из TZ §10.3
npx frugal meter bench/runs/<run-id>
npx frugal report bench/runs/       # отчёт и дашборд
```

Перед любым платным прогоном сначала запусти `--dry-run` (mock-модель). Серии > 2 прогонов запускай, только если оценил бюджет (`TZ.md` §10.7).

## 7. Как работать над пакетом WP-xx

1. Прочитай WP в `TZ.md` §16.3 и упомянутые разделы. Сверься с `docs/DECISIONS.md`.
2. Работай в своём git worktree и ветке потока (`TZ.md` §16.4). Реализуй пакет полностью, с тестами. Схемы данных из WP-00 меняй только через ADR.
3. Проверь DoD пакета по пунктам. Если пункт не выполнен, так и скажи; не помечай пакет готовым.
4. Обнови реестры, если затронуты:
   - новая идея → карточка в `docs/HYPOTHESES.md` (шаблон в `TZ.md` §19.2, ICS);
   - прогон → запись в `docs/EXPERIMENTS.md` (шаблон §19.3);
   - решение, отступление от ТЗ или изменение B0 → ADR в `docs/DECISIONS.md` (шаблон §19.4).
5. Отчитайся кратко: что сделано, как проверено, что осталось. Укажи проверенный коммит, команду, наблюдаемый результат и следующий доступный пакет. Для эксперимента приложи ID, манифест, качество и ссылки на исходные события.

Для параллельного пакета зафиксируй входной коммит, ожидаемые выходы и DoD. После интеграции запускай общий `--dry-run`. При изменении файла, зависимостей или снимка пересчитай относящийся к ним контекст. Если сокращённое представление неоднозначно, открой первичный артефакт. Каждый запрос к модели учитывай один раз, включая дочерние и служебные вызовы, оплаченные ретраи и работу оптимизатора. Пропуски в телеметрии отмечай явно. Сборка отчёта по сохранённым событиям выполняется офлайн.

## 8. Дрейф разрешён

Если по ходу находится идея **эффективнее** запланированной, её можно и нужно взять (процедура `TZ.md` §15): карточка → ICS → бюджет проверки → замер → принять или отклонить. Отрицательные результаты тоже записываются: они идут в отчёт.

## 9. Чего не делать

- Не запускать дорогие серии без dry-run и без записи в `EXPERIMENTS.md`.
- Не выдавать кэш-попадания за экономию сырых токенов: RPT и стоимость отчитываются раздельно (`TZ.md` §4.1).
- Не «чинить» B0, чтобы он выглядел хуже или лучше.
- Не трогать `TZ.md` §2.2, §4.3, §7, §10.1 без ADR и согласования с владельцем.
- Не замерять оптимизации, пока не пройден гейт Ф0 (замер и контур качества работают): такие цифры нельзя защитить.
- Не менять код `frugal` во время итоговой серии: серия идёт на замороженном git SHA.
