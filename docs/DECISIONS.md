### ADR-015. Учёт задач внутри общей сессии OpenCode

- **Дата и статус.** 22 ноября 2026, реализовано для офлайн-проверки WP-07.
- **Контекст.** При включённой капсуле две задачи могут получить отдельные запросы в одной сессии. События обеих задач могут иметь одинаковые временные метки.
- **Решение.** Для вызова `apply` с указанной задачей раннер сохраняет в `manifest.stages[].message_ids` идентификаторы сообщений из событий начала и окончания шага OpenCode. Измеритель сопоставляет с задачей пару `(session_id, message_id)`. Идентификаторы отдельных шагов по-прежнему различают несколько модельных вызовов в одном сообщении. Архивы без поля читаются по прежним правилам.
- **Проверка.** Тест запуска замораживает часы, продолжает сессию для второй задачи и сверяет построчно события, экспорт и принадлежность вызовов. Повторная атрибуция одного сообщения считается ошибкой учёта. [Тест запуска](../packages/cli/tests/run.test.ts) · [Проверки измерителя](../packages/cli/test/replay-session.test.ts)

### ADR-014. Приёмка оптимизированного ревью и архив полных логов

- **Дата и статус.** 21 ноября 2026, интегрировано для офлайн-проверок в `adbfdfe`.
- **Решение.** Оптимизированный протокол помечается `review_protocol: incremental` в независимых свидетельствах. Гейты требуют полного первого ревью, проверяемой дельты после реального изменения Git tree и отдельного полного sanity-ревью на итоговом дереве. Промежуточный `pass` допускает следующий полный раунд на том же дереве. Протокол входит в хеш подписываемого запроса. Свидетельства B0 без этой метки проверяются по прежним правилам.
- **Полный вывод.** Хук V1 помечает заменённый вывод хешем исходника. Раннер сверяет метку, путь и хеш, сохраняет полные байты под `raw/tool-output` и отклоняет попытку добавить полные логи в Git-снимок. После остановки исполнителя он собирает журналы дочерних сессий, чьи события отсутствуют в потоке CLI. Вывод с известными выданными ключами остаётся вне архива плагина. Модель может открыть сохранённый исходник по пути в рабочей копии.
- **Проверка.** Прошли 159 тестов TypeScript, включая публичные фикстуры капсул, review full → fix → delta → full sanity → verify и архив полного вывода. Работа OpenCode V1 1.19.6 и V2 2.3.2 проверена отдельными локальными вызовами оболочки и последующим чтением файла. Общая пара и ablation выполнены на синтетических данных. Живое сравнение требует закрытия Ф0 и проверки калибровки. [Правила обмена](collaboration/README.md) · [Исполнитель репетиции](../packages/cli/src/harness/optimized-replay.ts)

### ADR-013. Отдельные бюджеты когорт E0

- **Дата и статус.** 21 ноября 2026, реализовано в `fa518dd`.
- **Контекст.** Обе когорты M-M и M-L относятся к E0, а старый запуск читал только один файл бюджета `bench/plans/E0.json` с одной моделью. Анализатор привязывает наблюдения к точному идентификатору эксперимента.
- **Решение.** `--budget-plan <slug>` выбирает файл бюджета внутри `bench/plans/`. В манифестах сохраняется прежний идентификатор из `--experiment`. Для `--resume` в отпечаток серии входит выбранный план. Без нового флага действует прежний поиск файла по идентификатору эксперимента. Серия EXP-10 продолжает работу на закреплённом `f1f8742`.
- **Проверка.** Выбор разных когорт, фиксация плана при возобновлении, лимиты модели и бюджета проверены на фикстурах. Прошли сборка, 92 теста TypeScript, линт и парная репетиция. [Регистрация E0](E0_ANALYSIS.md) · [Команды раннера](../tools/runner/README.md)

### ADR-012. Параллельная подготовка оптимизаций

- **Дата и статус.** 21 ноября 2026, принято по просьбе владельца разделить работу с другом.

Подготовительные проверки не заменяют живых измерений и не закрывают гейты Ф0 или Ф1. [Договорённость о ветках](collaboration/README.md) · [Задания](collaboration/PROMPT_FOR_FRIEND.md)

### ADR-011. Короткий временный путь Docker на macOS

- **Дата и статус.** 21 ноября 2026, принято на `f1f8742` после Docker-репетиции и тестов.
- **Контекст.** Второй B0 EXP-08 остановился на `apply`. В последнем ответе модель передала искажённый абсолютный путь вне рабочей копии. Штатная проверка OpenCode заблокировала запись, после чего в исходном потоке отсутствует ответ с финальным `stop`.
- **Решение.** На macOS передавать Docker канонический короткий родитель `/private/tmp` для каталогов исполнителя. Каталоги создаются отдельно для каждого плеча с правами `0700`. Проверки границы монтирования и отказа записи вне рабочей копии сохраняются. Локальные прогоны продолжают использовать штатный каталог `tmpdir()`.
- **Проверка.** Сборка, 90 тестов и парная Docker-репетиция прошли. Для живого повтора зафиксированы новый SHA, прежний B0, требования, репозиторий, оракул и модель. [Сбой EXP-08](../bench/runs/summary/max-f0-second-f666fb4-1-base-a1-process-diagnostic.json) · [EXP-09](EXPERIMENTS.md#exp-20261121-09-повтор-ф0-с-коротким-путём-исполнителя)

### ADR-010. Повтор калибровки после двух сбоев раннера

- **Дата и статус.** 21 ноября 2026, предложено до проверки и закрепления нового SHA.
- **Контекст.** Две попытки DeepSeek max на `59bbe10` завершились до итогового снимка. В первой парсер классифицировал `BLOCKING: None found.` как блокирующее замечание. Во второй инструмент записи отклонил путь с ошибкой регистра в имени временного каталога. Обе попытки сохраняются как сбои процесса с полным учётом расходов. [EXP-20261121-07](EXPERIMENTS.md#exp-20261121-07-калибровка-deepseek-v41-flash-с-variant-max)
- **Решение.** Взять исправление формата вердикта `27aa095` и отдельно проверить уникальный суффикс временного каталога в нижнем регистре. Проверка точного пути и границы рабочего дерева обязательна. После интеграции зафиксировать новый SHA, проверить Docker dry-run и живой smoke с `opencode-go/deepseek-v4.1-flash --variant max`, затем провести два новых последовательных B0 с прежними требованиями и замороженным B0. В каждом слоте нужны независимая итоговая приёмка и полный проверяемый расход. [EXP-20261121-08](EXPERIMENTS.md#exp-20261121-08-повтор-deepseek-max-после-исправлений-раннера)
- **Последствия.** Сохраняются пороги Ф0 и протокол будущей пары. Перед каждым живым запуском и во время него проверяется недельная квота Go. При 50% и выше очередь и активный прогон останавливаются с сохранением известных событий. Лимит дополнительных списаний $0.
- **Уточнение владельца.** Во время первого B0 на `f666fb4` отменены порог 50% и ручной контроль недельного окна. Лимит дополнительных списаний остаётся $0. [EXP-08](EXPERIMENTS.md#exp-20261121-08-повтор-deepseek-max-после-исправлений-раннера)

### ADR-009. Основной профиль DeepSeek V4.1 Flash с максимальным reasoning

- **Дата и статус.** 21 ноября 2026, пользователь выбрал основной профиль. Допуск живой серии определяется результатами изолированных проверок и остатком квоты.
- **Решение.** Для первого валидного A/B используем `opencode-go/deepseek-v4.1-flash` с нативным `--variant max` во всех вызовах обоих плеч. До сравнения проверяем два автономных B0 в отдельной когорте. Замороженные промпты B0, публичные требования, снимок и независимый оракул общие для обоих плеч. Когорты DeepSeek с `provider-default` и Kimi хранятся под исходными ID, включая завершившийся после выбора модели прогон Kimi. Проверка на других моделях отложена до этапа обобщения. Минимальный объём и критерии E0–E10 определяет ТЗ. [Регистрация EXP-20261121-07](EXPERIMENTS.md#exp-20261121-07-калибровка-deepseek-v41-flash-с-variant-max)
- **Механизм.** Справка закреплённого OpenCode 1.19.6 подтверждает `opencode run --variant`. Каталог Go публикует `deepseek-v4.1-flash` через Chat Completions. DeepSeek для V4.1 Flash публикует уровни `low`, `high` и `max` и нативное поле `reasoning_effort`. В `3cb5140` раннер передаёт флаг каждому вызову `opencode run`, а локальный relay сохраняет наблюдаемое `reasoning_effort` и останавливает передачу при несовпадении. Квитанция живого smoke привязана к модели, варианту и закреплённому SHA. Замеры требуют отдельного живого подтверждения при нулевом списании. [DeepSeek Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/) · [DeepSeek Models](https://api-docs.deepseek.com/api/list-models/) · [Каталог OpenCode Go](https://models.opencode.ai/providers/opencode-go/)
- **Уточнение владельца после начала EXP-09.** Сохранить DeepSeek V4.1 Flash `max` и провести повтор на неизменном `f1f8742` с прежними параметрами. Предложение о смене модели снято до запуска другого профиля.

### ADR-008. Отдельный репозиторий приёмки

- **Дата и статус** — 21 ноября 2026, принято.
- **Решение.** Ветка независимой QA и её эталоны остаются в служебном worktree. В Git-историю исполнителя входит один автономный публичный снимок из `bench/repos/minibank.bundle`. В интеграционной ветке доступны публичный brief, ожидаемые поведения и агрегированные результаты контролей. Оценщик получает закрытый набор отдельно после остановки последнего процесса исполнителя.
- **Основание.** При попытке включить ветку с исходниками закрытых тестов в интеграционный checkout автоматическая проверка отклонила слияние из-за риска раскрытия. Раздельное размещение поддерживает требование §10.1 даже при разработке инструментов в основном worktree. Хеш набора фиксируется до запуска. Полные журналы закрытой приёмки остаются у проверяющего.

### ADR-007. Стандартный B0 и правило заморозки

- **Дата и статус** — 21 ноября 2026, принято. Ревизия исполнителя `22ddc08`.
- **Решение.** Используем штатные skills закреплённого OpenSpec, публичный brief целиком, одинаковую модель для всех ролей и естественное завершение ревью по §7. После каждого блокирующего замечания фиксируем входной снимок, исходный ответ и результат исправления. Неуспешная или неоднозначная проверка сохраняет всю попытку. Состав проекта и общие правила ID одинаковы в плечах.
- **Заморозка.** При первом калибровочном запуске сохранить SHA, хеш базовых шаблонов и ID в реестре. Синтетическая проверка транспорта выполняется отдельно. Подробности, штатные команды и правила завершения описаны в [контракте B0](baseline/B0.md).

### ADR-006. Контракты данных и среда воспроизведения

- **Дата и статус** — 21 ноября 2026, принято для WP-00.
- **Решение.** Используем npm workspaces и пакетный lock, uv с отдельным lock для анализа и демо-репозитория. Хост стенда зафиксирован в `.node-version`, точные версии каждого опыта сохраняются в манифесте. Обе линии opencode получают разные локальные бинарники. Компоненты RPT, исключение mock из экспериментов, состояние незавершённой попытки и ссылки на первичные данные описаны в [контрактах v1](DATA_CONTRACTS.md).
- **Проверка.** Запись одного вызова проходит JSON Schema, повторный импорт сверяет исходный поток и изолированную БД. Совпадение со счётчиком провайдера проверяется по отдельно сохранённому исходному usage. При расхождении или неизвестном расходе общий RPT остаётся неопределённым. Подробности в [описании измерителя](METER.md).

### ADR-005. Единая стратегия разработки Frugal SDD и два протокола ревью

- **Дата и автор** — 2026-11-21, Codex (PM).
- **Статус** — принято для объединённого плана. Готовность прототипа и результаты экспериментов проверяются отдельно.
- **Контекст.** Локальное ТЗ определяет прототип `frugal`, пакеты WP и серии E. В исходном коммите GitHub `271fb23` документ `SPEC.md` предлагает `sddbench`, пакеты W1–W7 и проверки P1–P4. Обе разработки находились на стадии планирования. [Исходный план GitHub](../SPEC.md) · [Техническое задание](../TZ.md)
- **Решение.** Агент начинает с единой [стратегии](../STRATEGY.md). Реализует один CLI `frugal` на TypeScript и общий плагин, ведёт WP-00…WP-16 и серии E по ТЗ. W1–W7 служат источником приёмочных проверок. P1 соответствует демонстрации основной пары, P2 — отдельной паре другого класса модели, P3 — проверке на другом репозитории, P4 — повторам и абляции. Выполнение отдельной пары фиксируется со своим объёмом доказательств. Статус завершения E определяется минимальным N и остальными условиями `TZ.md` §10.3. Основной KPI серии определяется §4.1. Из `SPEC.md` берём проверки инвалидации, полноты usage, отрицательные примеры качества и автономное воспроизведение отчёта.
- **Стенд.** Основной кандидат на фичу M — лимиты переводов из `TZ.md` §13. До утверждения в WP-01 приоритет у фичи, если её предоставят организаторы. Контракт `tickets export` из `SPEC.md` §4 пригоден для резервного стенда. Кандидаты для E5 — `yocto-queue` (JavaScript) и `google/uuid` v1.6.0 (Go). Для каждого требуется зелёная исходная база на закреплённой ревизии. [Снимок yocto-queue](https://github.com/sindresorhus/yocto-queue/tree/72a8fa96a9d389765cdf2bb9c6daba8302fc375d) · [Снимок google/uuid](https://github.com/google/uuid/tree/0f11ee6918f41a04c201eceeadf612a377bc7fbc)
- **Инструменты и модели.** Для основной серии используется opencode V1, для E10 — V2. Среда запуска всего стенда должна удовлетворять `engines` OpenSpec. Для 2.1.1 нужен Node ≥22.20.0, для 1.17.0 — ≥22.12.0. Для каждой пары до прогона фиксируются точные модель, провайдер и прочие настройки всех ролей. Модели, которыми Codex разрабатывает сам `frugal`, выбираются независимо от моделей измеряемого конвейера. [Манифест OpenSpec 2.1.1](https://registry.npmjs.org/@fission-ai%2fopenspec/2.1.1) · [Манифест 1.17.0](https://registry.npmjs.org/@fission-ai%2fopenspec/1.17.0)
- **Ревью.** В B0 (`TZ.md` §7) обязателен один содержательный LLM-проход, затем цикл продолжается при открытых блокирующих замечаниях, максимум до пяти итераций. Для конкурсной фичи готовим 8–12 задач. Если обычная полная пара проходит 3–5 реальных раундов в каждом плече, она даёт нужную демонстрацию. До просмотра пар регистрируем условие отдельного демонстрационного сценария `D-review` на случай выхода за этот диапазон. В `D-review` оба плеча выполняют три содержательных ревью по одинаковой программе (контракт, границы и тесты, итоговая согласованность). После каждого раунда записываются SHA, вывод и судьба замечаний. Ещё до двух раундов отводятся на перепроверку оставшихся проблем по одинаковому правилу. По исчерпании лимита открытая блокирующая проблема означает провал приёмки. Полный путь, включая исправления, измеряется в каждом плече. Данные `D-review` хранятся под собственными run ID и показываются отдельно от результатов B0/E3. [Слайды 29–32](../docs/source/hackathon-presentations.pdf#page=29)
- **Последствия.** Подготовку обоих стендов, независимого эталона, измерителя и сборки отчёта можно вести параллельно. Переходы между измерительными фазами и правила заморозки определяет `TZ.md` §16. Сборку отчёта и воспроизведение артефактов проверяет отдельный агент на чистом checkout. Источники и решения доступны в Git, экспериментальные цифры формируются из `bench/runs/`.

### ADR-004: Стек решения
- **Дата / автор:** 2026-11-21 / PM
- **Статус:** Предложено
- **Контекст:** плагины opencode пишутся на TS, OpenSpec работает на Node; для анализа данных удобнее Python.
- **Решение:** CLI и плагин на TypeScript (Node ≥ 20, ESM, vitest), анализ и отчёт на Python (uv, pandas, matplotlib/plotly).
- **Альтернативы:** всё на TS (меньше стеков, но статистика и графики дольше); всё на Python (плагин всё равно TS).
- **Последствия:** целевому репо нужен только Node (он и так нужен для opencode и OpenSpec). Python нужен только нам.

### ADR-003: Конвенция трассировки общая для обеих веток
- **Дата / автор:** 2026-11-21 / PM
- **Статус:** Предложено
- **Контекст:** чтобы честно и дёшево измерять INV-1 (100 % покрытие) в обеих ветках, нужны ID требований, сценариев и задач.
- **Решение:** ID-правила записываются в `openspec/config.yaml` демо-репо и действуют в B0 и opt одинаково. Экономию `frugal` даёт не сама конвенция, а детерминированные инструменты поверх неё (капсула, трассировка, verify). Если B0-агент не соблюдает конвенцию, используется `frugal trace --infer`, а его токены не входят в RPT конвейера.
- **Альтернативы:** ID только в opt (сложнее и дороже измерять B0, есть риск претензии «вы сравниваете разные процессы»).
- **Последствия:** см. `TZ.md` §6.4, §9.2.

### ADR-002: Основная метрика: сырые обработанные токены (RPT)
- **Дата / автор:** 2026-11-21 / PM
- **Статус:** Предложено
- **Контекст:** кэш провайдера снижает стоимость, но не число токенов, которые обработала модель. Жюри оценивает «% экономии, подтверждённый замером».
- **Решение:** основной KPI — RPT = вход (без кэша) + чтение кэша + запись кэша + выход + reasoning. Стоимость (M4) и доля кэша (M6) отчитываются отдельно.
- **Последствия:** H-09 (кэш-раскладка) не влияет на основной KPI. Это честно и защищает от вопросов жюри.

### ADR-001: Версии opencode и OpenSpec
- **Дата / автор:** 2026-11-21 / PM
- **Статус:** Предложено (подтвердить стартовыми проверками: OQ-9, OQ-10)
- **Контекст:** opencode разделён на V1 (`opencode-ai` 1.19.6) и V2 (`@opencode/cli` 2.3.2), плагины несовместимы. OpenSpec 2.1.1 перевёл всё на skills в `.agents/skills/` и по умолчанию ставит их глобально.
- **Решение:** opencode V1 1.19.6 (зрелый API плагинов, совместимость с tokenscope и DCP для сверки и E8); плагин `frugal` с двойным экспортом V1/V2, работающий на обеих линиях (V2 проверяется в E10). OpenSpec 2.1.1 с `--scope project`. Если opencode V1 не видит `.agents/skills/`, переходим на OpenSpec 1.17.0.
- **Альтернативы:** V2 (новее, но экосистема плагинов не готова и нет LSP).
- **Последствия:** все версии закрепляются локально в харнессе и пишутся в манифест.
