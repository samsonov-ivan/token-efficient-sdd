# Промпт для Codex друга

Ты ведёшь разработку трёх оптимизаций Frugal SDD в репозитории `https://github.com/samsonov-ivan/token-efficient-sdd`. Владелец параллельно ведёт контрольные запуски, приёмку, измерение и интеграцию. Изменения передавайте через Git по инструкции `docs/collaboration/README.md`.

1. Найди локальный checkout репозитория или клонируй его. Проверь `git status --short` и `git remote -v`. Если есть незакоммиченные изменения, используй отдельный worktree. Выполни `git fetch origin`. Переключись на свою ветку `codex/frugal-friend`. Если её ещё нет локально, выполни `git switch --track origin/codex/frugal-friend`. Выполни `git pull --ff-only` в своей ветке. Затем запусти `node scripts/peer-sync.mjs status` и прочитай обновления владельца. Текущая интеграционная ветка — `origin/codex/frugal-integration`.
2. Прочитай `AGENTS.md`, `docs/STATE.md`, `docs/collaboration/README.md`, записи ADR-009, ADR-011 и ADR-012 в `docs/DECISIONS.md`, а также пакеты WP-07, WP-08 и WP-09 в §16.3 `TZ.md`. Используй закреплённые локальные инструменты. Если делегируешь задачи агентам, выбирай уровень рассуждения `high`. При использовании нескольких worktree своди проверенные коммиты в свою ветку перед публикацией.
3. Возьми три задачи ниже. До завершения калибровки делай прототипы за независимыми флагами и проверяй их на открытых фикстурах и mock. Используй публичный контракт, сохрани исходные требования и запрет доступа к закрытым тестам. B0 и его шаблоны заморожены. За исключением предусмотренных флагами изменений оптимизированного плеча, все стадии и проверки качества сохраняются. Модельные API для этих задач не нужны. Для снимка замера, смены контрактов или разрешения реальных вызовов запиши вопрос владельцу в `docs/collaboration/friend.md`.

Для отдельно согласованных живых прогонов используй `OPENCODE_API_KEY` из локального игнорируемого `.env`. В исходниках, Git-заметках и отчётах указывай только имя переменной.

| Твоя задача | Что сделать | Проверка на открытых данных |
|---|---|---|
| Капсула задачи · WP-07, H-02 | Реализовать `frugal capsule <change> <task>`. Собрать текст задачи, связанные требования и сценарии дословно, нужные части design, handoff и путь к полным материалам. Использовать формат `flags.capsule` из реестра. | Повторный вызов с одинаковым входом даёт одинаковый вывод. Обязательные блоки и путь к полному тексту присутствуют. При отсутствующей или висящей ссылке команда выдаёт явную диагностику. |
| Сжатие вывода инструментов · WP-08, H-03 | Реализовать `flags.tool_output_compression`. Начать с журналов pytest, Vitest и git. Сохранять полный вывод на диск и возвращать сводку со ссылкой на него. Сохранить загрузку существующих входов плагина V1 и V2. | Фикстуры проверяют, что ошибки, assertion и предупреждения остаются в сводке, полный файл побайтно совпадает с входом, незнакомый формат доступен целиком и выключенный флаг сохраняет прежнее поведение. |
| Ревью по изменениям · WP-09, H-05/H-06/H-23 | Подготовить модуль для оптимизированного плеча. Первое ревью получает полный diff и чек-лист, повторное — diff исправления и открытые замечания. Валидировать `findings.json` по `schemas/findings.schema.json`. Сохранить итоговую полную проверку и стадию verify. | Фикстуры проверяют, что блокирующее замечание не теряется между раундами, некорректный JSON отклоняется, а при отсутствии опорного снимка доступно полное ревью. Штатный B0 не меняется. |

После первой заметки о начале работы и после каждого завершённого блока обновляй `docs/collaboration/friend.md`. Указывай результат, команду проверки, следующий шаг и конкретный вопрос, если он есть. Проверяй изменения локально и публикуй каждый готовый коммит сразу, не дожидаясь остальных блоков.

```sh
git add <файлы-твоей-задачи> docs/collaboration/friend.md
git commit -m "feat(frugal): describe the completed change"
node scripts/peer-sync.mjs publish
node scripts/peer-sync.mjs status
```

Перед переходом к следующему блоку и во время длительного ожидания обновляй статус. Если публикация отклонена, сначала выполни `git pull --ff-only` из своей ветки. При расхождении истории оставь локальные коммиты и сообщи владельцу. Не используй force push и не публикуй чужие ветки. Пропускай `.env`, ключи, сырые прогоны и закрытые тесты при подготовке коммита. Удалённую ветку `main` интегрирует владелец по отдельному решению.
