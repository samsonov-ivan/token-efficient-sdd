# OpenSpec (Fission-AI/OpenSpec, npm @fission-ai/openspec): technical reference for a token-saving layer (state as of 2026-11-21)

Method note: almost everything below comes from primary sources. I downloaded the npm tarball `@fission-ai/openspec@2.1.1` and read it as data without running it. I also shallow-cloned the GitHub repo at commit `0c737dc` (2026-11-19 22:15 UTC, matching the 2.1.1 release). Paths are cited as GitHub `main` URLs. Token estimates are my own measurements using a chars/4 heuristic (plus words×1.33 as a cross-check). No real tokenizer was available, so treat them as approximate. Russian/Cyrillic text tokenizes less efficiently than English, so the same artifact written in Russian will cost more tokens.

IMPORTANT: the repo has two doc trees. `docs/` still describes the 1.x layout (command files `/opsx:*` next to skills). `docs-lab/` describes 2.x (skills only, shared `.agents/skills/`). Where they disagree, the 2.x source code and `docs-lab/` reflect the current release.

## 1. Versions, release history, 0.x → 1.x (OPSX) → 2.x; skills vs commands; what `openspec init` generates for opencode

### Takeaway
The current latest is **2.1.1 (2026-11-19)**. 2.0.0 (2026-11-11) removed all `/opsx:*` command files: every workflow is now a skill named `openspec-*`. Skills are written once to `.agents/skills/`, and since 2.1 they install **globally by default** (`~/.agents/skills/`) unless `--scope project` is given. For opencode, 2.x writes `.agents/skills/openspec-*/SKILL.md` (project scope) and you invoke e.g. `/openspec-apply-change`. 1.x wrote `.opencode/skills/openspec-*/SKILL.md` plus `.opencode/commands/opsx-<id>.md` (`/opsx-propose`). If the hackathon baseline says "/opsx:propose, /opsx:apply…", that is 1.x vocabulary: pin a version deliberately.

### Inferences
- Baseline reproducibility: pin the exact version (e.g. `npm i -g @fission-ai/openspec@2.1.1`). Use `openspec init --scope project --tools opencode` so the skills live in the repo (`.agents/skills/openspec-*/SKILL.md`), are versioned, and are measurable. A global install hides them from the repo and makes A/B token comparisons harder.
- If the case materials literally require `/opsx:*` commands in opencode, that means 1.x (≤1.17.0). 1.17.0 is the last release that generates `.opencode/commands/opsx-<id>.md`. On 2.x the same instructions arrive as skills.
- Because `openspec update` overwrites built-in skill folders, a token-saving layer should not edit `openspec-*` skills in place. Ship its own skills, a custom schema, or a wrapper.

### Gaps
- I did not verify how opencode itself discovers `.agents/skills/` (opencode docs not fetched). The claim relies on OpenSpec's support matrix.
- Size of the 0.x `openspec/AGENTS.md` instructions not measured.

## 2. CLI reference (2.1.1) and machine-readable `--json` outputs

### Takeaway
The CLI is deterministic (no LLM) and has rich `--json` modes. `status`, `instructions`, `show`, `list`, `validate`, `archive`, `new`, `templates`, `schemas`, `context` and `update --dry-run` are designed for agents to call. The most useful outputs for slicing are: `instructions apply --json` (tasks with `id/description/done/sourcePath/line`), `show <change> --json` (deltas with requirement `name/text/scenarios[name,rawText]`), and `show <spec> --type spec --json [--no-scenarios | -r N]`.

### Cited Findings
- **Command groups:** Set up: `init`, `update`, `config`. Changes/specs: `list`, `show`, `view`, `validate`, `archive`. Workflow/schemas: `new`, `status`, `instructions`, `templates`, `schemas`, `schema`. Multi-repo (beta): `store`, `doctor`, `context`, `workset`. Utilities: `version`, `install`, `feedback`, `completion`. **Deprecated:** noun forms `openspec change …` / `openspec spec …` ("The CLI warns and points to the verb-first commands") — [docs-lab/reference/cli.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- **`init [path]`** flags: `--tools <ids|all|none>`, `--language <lang>`, `--force`, `--profile core|custom`, `--no-animation`, `--copilot-cloud`, `--scope global|project`. Tool ids include `opencode`, `claude`, `codex`, `cursor`, `agents` (vendor-neutral) and others — [cli.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md); [docs/supported-tools.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/supported-tools.md)
- **`update`** refreshes installed skills. `openspec update --dry-run` (with `--json`) reports files to add/change/delete without writing (since 1.15.0) — [CHANGELOG 1.15.0](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- **`list`** `[--specs|--changes|--archived|--all] [--sort recent|name] [--json] [--store <id>]`. JSON: `{"changes":[{"name","completedTasks","totalTasks","lastModified","status":"no-tasks|in-progress|complete"}],"root":{"path","source"}}` — [cli.md#openspec-list](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- **`show <item>`** flags: `--json`, `--type change|spec`, `--no-interactive`, `--deltas-only` ("Change JSON is already delta-only, so output matches plain `--json`"), `--requirements-only` (deprecated alias), `--diff`, `--requirements`/`--no-scenarios` (spec JSON with emptied `scenarios`), `-r, --requirement <id>` ("output one requirement by 1-based position"). Text mode is "a raw passthrough": a change prints its `proposal.md`, a spec its `spec.md` — [cli.md#openspec-show](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- **Change JSON shape:** `{"id","title","deltaCount","deltas":[{"spec":"api","operation":"ADDED","description":"Add requirement: …","requirement":{"name":"Rate limit","text":"The API SHALL …","scenarios":[{"name":"Client exceeds the limit","rawText":"- **WHEN** … \n- **THEN** …"}]}}],"root":{…}}`. With `--json --diff`, MODIFIED deltas gain `diff`/`warning` strings. `name` fields were added in 1.14.0 "so JSON readers can cite a requirement without parsing the markdown again" — [cli.md#openspec-show](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md); [CHANGELOG 1.14.0 #1972](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- **Spec JSON shape:** `{"id","title","overview","requirementCount","requirements":[{"name","text","scenarios":[{"name","rawText"}]}],"metadata":{"version":"1.0.0","format":"openspec"},"root":{…}}` — [cli.md#openspec-show](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- 1.13.1 fixed `show --json --deltas-only` so it "report[s] the deltas archive applies" (before, the parser behind it could diverge from archive) — [CHANGELOG 1.13.1 #1856](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- **`view`** prints a one-screen dashboard (Draft/Active/Completed changes, specs by requirement count, per-change artifact markers `proposal✓ specs→ design→ tasks✓`). It has no JSON mode and no longer lists archived changes (1.14.1) — [cli.md#openspec-view](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- **`validate [item]`** flags: `--all|--changes|--specs|--archived`, `--strict` ("Treat warnings as failures"), `--type`, `--json`, `--report full|findings`, `--concurrency <n>` (default `OPENSPEC_CONCURRENCY` or 6), `--no-interactive`, `--store`. JSON: `{"items":[{"id","type","valid","issues":[{level:"ERROR|WARNING|INFO", …optional line/column}],"durationMs"}],"summary":{"totals":{items,passed,failed},"byType":{…}},"version":"1.0","root":{…}}`. `--report findings --json` gives `{"report":{"kind":"validation-findings","version":"1.0","scope","returnedItems","totalItems"},"itemFindings":[…],"summary",…}`. Exit 1 on any failure or on an unreadable/invalid `openspec/config.yaml` — [cli.md#openspec-validate](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- Validate also dry-runs archive's merge builder and reports merge conflicts (missing MODIFIED target, conflicting ADDED) as `INFO`, which "never changes the exit code, including under `--strict`" — [cli.md#openspec-validate](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- `validate --archived` (1.9.0) checks that every archived change has all checkboxes ticked — [CHANGELOG 1.9.0](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- **`archive <change>`** flags: `-y/--yes`, `--skip-specs`, `--no-validate`, `--json` (needs `--yes`), `--store`. It moves the change to `openspec/changes/archive/YYYY-MM-DD-<name>/` and merges deltas into `openspec/specs/<cap>/spec.md`. JSON: `{"archive":{"change","archivedAs","path","specsUpdated","totals":{added,modified,removed,renamed}},"root":{…}}`. "Incomplete tasks warn but don't block" — [cli.md#openspec-archive](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- **`new change <name>`** flags: `--description`, `--goal`, `--schema`, `--json`. It creates only `.openspec.yaml` (`schema: spec-driven`, `created: YYYY-MM-DD`). "Artifacts … aren't scaffolded here" — [cli.md#openspec-new](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- **`status --change <id> | --all`** with `--schema`, `--json`. Text shows `[x]` done, `[ ]` ready, `[-]` blocked, plus a `Next:` line (e.g. `openspec instructions apply --change "x" --json`). JSON: `{"changeName","schemaName","isComplete","nextSteps":[…],"artifacts":[{"id","outputPath","status":"done|ready|blocked|skipped","requires":[…],"missingDeps":[…]}]}`. `--all --json` returns `{"changes":[…],"root"}` in one process (1.11.0) — [cli.md#openspec-status](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md); [CHANGELOG 1.11.0](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- Status JSON also carries `planningHome`, `changeRoot` and `actionContext` (with `allowedEditRoots`), which the apply skill parses — [skills/openspec-apply-change/SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-apply-change/SKILL.md); [CHANGELOG 1.14.0 #2014](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- **`instructions <artifact|apply|archive> --change <id> [--schema] [--json]`**. Text form uses XML-ish blocks `<artifact id=… change=… schema=…>`, `<task>`, `<output>Write to: …</output>`, `<instruction>…`. Artifact JSON fields: `changeName, artifactId, schemaName, changeDir, outputPath, existingOutputPaths, instruction, template, dependencies, unlocks, root` (source interface also has `planningHome`, `context`, `rules`, `references`) — [cli.md#openspec-instructions](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md); [src/core/artifact-graph/instruction-loader.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/artifact-graph/instruction-loader.ts)
- **Apply JSON** carries `contextFiles` (artifact ID → array of file paths), `progress` (total/complete/remaining), `tasks`, `taskTrackingConfigured`, `state` (`blocked|ready|all_done`), `instruction`, and optional `context`, `operationGuidance`, `missingArtifacts`, `unavailableTrackingFiles`. "Each `tasks` entry carries `id`, `description`, `done`, `sourcePath`, and `line`". Wrapped multi-line tasks come back as one line (fixed in 2.0.0). Text apply output lists Context Files (paths), Progress, Tasks, Instruction ("Read context files, work through pending tasks, mark complete as you go. Pause if you hit blockers or need clarification.") — [cli.md#openspec-instructions](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md); [apply SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-apply-change/SKILL.md); [CHANGELOG 2.0.0 #2228](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- `contextFiles` are **paths, not contents**. The agent reads the files itself — [cli.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- **`templates [--schema] [--json]`** returns a map artifact→{path, source: project|user|package}. **`schemas [--json]`** lists schemas with artifact order. **`schema which|validate|fork|init`** (experimental) — [cli.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- **`context [--json]`** prints the working context: the OpenSpec root plus referenced stores "each with a fetch command" (e.g. `openspec show <spec-id> --type spec --store team-context`). The propose skill runs `openspec context --json` first — [cli.md#openspec-context](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md); [skills/openspec-propose/SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-propose/SKILL.md)
- Performance: `--json` commands skip loading the `ora` spinner, and `status --json` loads 163 modules instead of 186 (1.15.0). Lazy command loading cut `--version` to 24 modules instead of 485 (1.14.1) — [CHANGELOG](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- Telemetry: anonymous command names and version only, off in CI. Opt out with `OPENSPEC_TELEMETRY=0` or `DO_NOT_TRACK=1` — [docs/faq.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/faq.md)

### Inferences
- A token-saving orchestrator can do all state handling (which change, which artifact is next, which task is pending, done/not done, validation) through `status --json`, `instructions apply --json` and `validate --strict --json` without spending LLM tokens. The built-in skills make the LLM run and parse these commands itself.
- `show <change> --json` and `show <spec> --type spec --json -r N` are the native primitives for building per-task requirement slices: one requirement plus its scenarios, rather than whole files.
- `openspec archive <id> -y --json` performs the delta merge deterministically. Calling it from the orchestrator avoids the ~4.5k-token archive skill and any LLM-driven sync.

### Gaps
- `instructions apply --json` and `status --json` contain more fields than the docs list (the docs say "Trimmed"). Exact full shapes should be captured by running the CLI in a sandbox. I deliberately did not execute the downloaded package.
- The `-r <id>` flag selects by **position** (1-based), not by a stable ID, so it is fragile under edits.

## 3. Artifact formats: delta specs, tasks.md, proposal.md, design.md, .openspec.yaml, config.yaml, custom schemas

### Takeaway
The layout is `openspec/specs/<capability>/spec.md` (source of truth), `openspec/changes/<id>/{.openspec.yaml, proposal.md, design.md, tasks.md, specs/<capability>/spec.md}` (delta specs), and `openspec/changes/archive/YYYY-MM-DD-<id>/`. Delta specs use `## ADDED|MODIFIED|REMOVED|RENAMED Requirements`, `### Requirement: <name>`, and `#### Scenario: <name>` with `- **WHEN**`/`- **THEN**`. Tasks are checkboxes `- [ ] X.Y …` under `## N. Group`. The artifact DAG is defined in `schema.yaml` and is fully overridable per project (`openspec/schemas/<name>/`).

### Cited Findings
**spec-driven schema (package `schemas/spec-driven/schema.yaml`, version 1):**
- Artifacts and dependencies: `proposal` (generates `proposal.md`, requires `[]`) → `specs` (generates `"specs/**/*.md"`, requires `[proposal]`) and `design` (generates `design.md`, requires `[proposal]`) → `tasks` (generates `tasks.md`, requires `[specs, design]`). The apply block is `apply: { requires: [tasks], tracks: tasks.md, instruction: "Read context files, work through pending tasks, mark complete as you go. Pause if you hit blockers or need clarification." }` — [schema.yaml](https://unpkg.com/@fission-ai/openspec@2.1.1/schemas/spec-driven/schema.yaml)
- The design instruction says to create design.md "only if any apply": cross-cutting change, new dependency or data model, security/performance/migration complexity, or ambiguity. Even so, `tasks` requires `design` in the DAG — [schema.yaml](https://unpkg.com/@fission-ai/openspec@2.1.1/schemas/spec-driven/schema.yaml)

**Delta spec rules (from the specs instruction and the validator):**
- Delta ops: "**ADDED Requirements**: New capabilities; **MODIFIED Requirements**: Changed behavior - MUST include full updated content; **REMOVED Requirements**: … MUST include **Reason** and **Migration**; **RENAMED Requirements**: Name changes only - use FROM:/TO: format" — [schema.yaml](https://unpkg.com/@fission-ai/openspec@2.1.1/schemas/spec-driven/schema.yaml)
- Format: "Each requirement: `### Requirement: <name>`… Use SHALL/MUST for normative requirements… Each scenario: `#### Scenario: <name>` with WHEN/THEN format… **CRITICAL**: Scenarios MUST use exactly 4 hashtags… Every requirement MUST have at least one scenario. Every scenario MUST have a WHEN/GIVEN step… and a THEN step" (a missing step is a warning that fails under `--strict`, since 1.16.0) — [schema.yaml](https://unpkg.com/@fission-ai/openspec@2.1.1/schemas/spec-driven/schema.yaml); [CHANGELOG 1.16.0](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- The RENAMED parser regex is `^\s*[-*+]?\s*FROM:\s*\`?###\s*Requirement:\s*(.+?)\`?\s*$` (and the same for `TO:`). So the syntax is `- FROM: \`### Requirement: Old\`` followed by `- TO: \`### Requirement: New\`` — [src/core/parsers/requirement-blocks.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/parsers/requirement-blocks.ts)
- MODIFIED workflow: "Copy the ENTIRE requirement block (from `### Requirement:` through all scenarios)… Ensure header text matches exactly (whitespace-insensitive)… Using MODIFIED with partial content loses detail at archive time" — [schema.yaml](https://unpkg.com/@fission-ai/openspec@2.1.1/schemas/spec-driven/schema.yaml)
- New capabilities start with `## Purpose` (≥50 chars, otherwise too brief under `--strict`). The delta template is `# Spec Delta / ## Purpose / ## ADDED Requirements / ### Requirement: / #### Scenario: - **WHEN** - **THEN**` — [templates/spec.md](https://unpkg.com/@fission-ai/openspec@2.1.1/schemas/spec-driven/templates/spec.md)
- Validator constants: `MIN_WHY_SECTION_LENGTH = 50`, `MAX_WHY_SECTION_LENGTH = 1000`, `MIN_PURPOSE_LENGTH = 50`, `MAX_REQUIREMENT_TEXT_LENGTH = 500`, `MAX_DELTAS_PER_CHANGE = 10` ("Consider splitting changes with more than 10 deltas"). A delta description must be ≥10 chars — [src/core/validation/constants.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/validation/constants.ts); [validator.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/validation/validator.ts)
- A requirement over 500 chars became a WARNING in 1.14.1, so `--strict` fails. 2.1.1 also warns when a MODIFIED requirement grows past 500 relative to its baseline — [CHANGELOG 1.14.1, 2.1.1](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- An unrecognized `## … Requirements` section (e.g. `## DEPRECATED Requirements`) now fails validate, and archive refuses it (1.16.1). Text outside known sections is warned as not carried into the main spec (1.14.2) — [CHANGELOG](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- A zero-delta change is rejected unless `.openspec.yaml` sets `skip_specs: true` — [templates/proposal.md](https://unpkg.com/@fission-ai/openspec@2.1.1/schemas/spec-driven/templates/proposal.md)

**tasks.md:**
- Template: `# Tasks / ## 1. <Group> / - [ ] 1.1 … / - [ ] 1.2 … / ## 2. …`. Rules: "Each tracked task MUST be a checkbox: `- [ ] X.Y Task description`"; "Each task MUST state how to verify completion (a test, command, observable behavior, or delivered artifact)"; "Each task group MUST land the tests and documentation its own work calls for. Do NOT collect testing or documentation into a final group"; post-archive steps go as plain bullets under `## Workflow follow-up` — [schema.yaml](https://unpkg.com/@fission-ai/openspec@2.1.1/schemas/spec-driven/schema.yaml); [templates/tasks.md](https://unpkg.com/@fission-ai/openspec@2.1.1/schemas/spec-driven/templates/tasks.md)
- Only `x`/`X` counts as done. `- [~]`, `- [-]` and `- []` read as unfinished. Any list marker (`-`, `*`, `+`, `1.`, `2)`) works. A file with no checkbox counts as 0 tasks (validate WARNING). Duplicate task IDs at full depth produce a warning (1.9.0) — [schema.yaml](https://unpkg.com/@fission-ai/openspec@2.1.1/schemas/spec-driven/schema.yaml); [schema-yaml.md#tracks](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/schemas/schema-yaml.md); [cli.md#openspec-validate](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md); [CHANGELOG 1.9.0](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)

**proposal.md / design.md:**
- Proposal template sections: `## Why`, `## What Changes`, `## Capabilities` (`### New Capabilities` / `### Modified Capabilities`, kebab-case `<capability-path>`), and `## Impact`. The instruction says "Keep it concise (1-2 pages)" — [templates/proposal.md](https://unpkg.com/@fission-ai/openspec@2.1.1/schemas/spec-driven/templates/proposal.md); [schema.yaml](https://unpkg.com/@fission-ai/openspec@2.1.1/schemas/spec-driven/schema.yaml)
- Design template sections: `## Context`, `## Goals / Non-Goals`, `## Decisions`, `## Risks / Trade-offs`. The instruction adds Migration Plan and Open Questions, and says "Reference the proposal for motivation instead of restating it" — [templates/design.md](https://unpkg.com/@fission-ai/openspec@2.1.1/schemas/spec-driven/templates/design.md); [schema.yaml](https://unpkg.com/@fission-ai/openspec@2.1.1/schemas/spec-driven/schema.yaml)

**`.openspec.yaml` (per change):**
- Fields: `schema` (required), `created` (YYYY-MM-DD), `goal`, `affected_areas` (list), `initiative` ({store,id}), `skip_specs` (bool), `retire_capabilities` (bool). **Extension keys**: any top-level key starting with lowercase `x-` (e.g. `x-tracker: SB-5497`) "OpenSpec does not read or validate it". It passes `--strict` (since 1.14.2) and moves with the archive — [change-metadata.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/configuration/change-metadata.md)
- Unknown non-`x-` keys produce warnings (and fail `--strict`) — [change-metadata.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/configuration/change-metadata.md)

**`openspec/config.yaml` (per project):**
- Fields: `schema` (required), `context` (string "Injected into every artifact, apply, and archive", limit 50KB), `rules` (artifact ID → list of strings), `operations` (`apply`/`archive` → `guidance:` list, advisory), `store`, `references` (store ids whose spec *index* is added to instructions: "Spec content is never inlined"), `skillsScope`. "Invalid fields never fail a command… a bad value is dropped with a warning" (except `validate`, which exits 1 on unreadable YAML). `config.yml` is a legacy alias — [config-yaml.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/configuration/config-yaml.md)
- A known pitfall: a `rules:` item containing an unquoted `": "` parses as a mapping and drops that artifact's whole rule set (warning only) — [CHANGELOG 1.14.0 #1984](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- Global CLI config lives at `~/.config/openspec/config.json` (`profile`, `workflows`, `delivery` [retired], `skillsScope`, `defaultStore`, `featureFlags`, `telemetry`) — [config-json.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/configuration/config-json.md)

**Custom schemas:**
- Lookup order is project `openspec/schemas/<name>/`, then user `~/.local/share/openspec/schemas/<name>/` (or `$XDG_DATA_HOME`), then package. Top-level fields: `name`, `version`, `description`, `artifacts[]`, `apply`. Artifact fields: `id`, `generates` (path/glob), `description`, `template`, `instruction` (optional), `requires`. Apply fields: `requires`, `tracks` (path/glob, e.g. `"**/tasks.md"` — "OpenSpec combines their tasks and progress"), `instruction`. Completion is file-existence only ("It doesn't read the file to decide whether the artifact is complete") — [schema-yaml.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/schemas/schema-yaml.md)
- Tools: `openspec schema fork`, `schema init`, `schema validate` (checks types, relative paths, ids/deps/cycles, apply.requires, templates). It does not catch misspelled fields like `instrution` — [schema-yaml.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/schemas/schema-yaml.md)
- Open issue #1694: config.yaml's context/rules are not scoped per schema and leak across schemas in one project — [issue search result #1694](https://github.com/Fission-AI/OpenSpec/issues/1694)

### Inferences
- You can fork `spec-driven` into a project schema (e.g. `spec-driven-lean`) to (a) shorten artifact `instruction`s, (b) change `apply.tracks` to `tasks/*.md` for per-group task files, and (c) add an artifact such as `trace.md` or `tests` with its own `requires`. This needs no source change, and `openspec update` won't overwrite project schemas.
- `x-` keys in `.openspec.yaml` are a sanctioned place for orchestrator metadata (e.g. a requirement→task map digest or a token budget) that survives `validate --strict` and archive.
- `config.yaml` `context` is injected into every artifact/apply/archive instruction. Keeping it to a few lines (or moving it to on-demand files) is a direct saving: every byte is paid once per instruction fetch.

### Gaps
- I did not verify whether `context` and `rules` are re-sent in full on every `instructions apply --json` call. The docs say apply includes `context` and `operationGuidance`, so it likely is.

## 4. What text the agent receives: skill and instruction sizes (token cost per stage)

### Takeaway
Each OpenSpec skill body is roughly **1.2k–5.9k tokens**. Apply is ~2.2–2.8k, propose ~3.3–4.2k, verify ~3.9–5.1k, archive ~3.6–4.5k and explore ~4.5–5.9k. Per-artifact CLI instructions add another ~0.4–1.7k tokens (the `specs` instruction alone is ~1.7k), on top of `context`/`rules`/template. The apply skill tells the agent to read **every** context file (proposal, all delta specs, design, tasks) and to re-run `openspec instructions apply --json` after **every** task. That makes it the main per-task cost multiplier.

### Cited Findings
- Measured SKILL.md sizes in repo `skills/` ("the same skill `openspec init` writes into a project", generated from templates). Bytes / my token estimate (chars/4 – words×1.33):
  - `openspec-apply-change` 11,242 B, ~2.8k / ~2.2k tok
  - `openspec-propose` 16,637 B, ~4.2k / ~3.3k
  - `openspec-verify-change` 20,462 B, ~5.1k / ~3.9k
  - `openspec-archive-change` 17,989 B, ~4.5k / ~3.6k
  - `openspec-sync-specs` 15,761 B, ~3.9k / ~3.2k
  - `openspec-explore` 23,408 B, ~5.9k / ~4.5k
  - `openspec-ff-change` 11,606 B, ~2.9k / ~2.3k
  - `openspec-continue-change` 10,669 B, ~2.7k / ~2.2k
  - `openspec-update-change` 11,249 B, ~2.8k / ~2.3k
  - `openspec-new-change` 5,877 B, ~1.5k / ~1.2k
  - `openspec-onboard` 16,809 B, ~4.1k / ~3.4k
  - `openspec-bulk-archive-change` 23,017 B, ~5.7k / ~4.4k
  - Sources: [skills/README.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/README.md); [skills/](https://github.com/Fission-AI/OpenSpec/tree/main/skills) (sizes measured by me)
- Artifact instruction strings in `schema.yaml` (served by `openspec instructions <artifact>`): proposal 3,017 chars (~750 tok), specs 6,765 (~1.7k), design 1,709 (~430), tasks 2,803 (~700), apply 122 chars. Templates: proposal 1,468 B, spec 374 B, design 417 B, tasks 218 B — [schema.yaml](https://unpkg.com/@fission-ai/openspec@2.1.1/schemas/spec-driven/schema.yaml) (measured by me)
- Every skill carries a shared preamble ("Store selection…", "Project check… run `openspec list --json`…", plus branches for auto-selected vs explicit use) before the actual steps — [apply SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-apply-change/SKILL.md)
- Apply skill steps: (1) select change; (2) `openspec status --change "<name>" --json`; (3) `openspec instructions apply --change "<name>" --json`; (4) "Read every file path listed under `contextFiles`… spec-driven: proposal, specs, design, tasks"; (6) per task, "Mark the task complete at its returned `sourcePath` and `line`… Rerun the apply instructions and confirm that task is now done and progress changed". Guardrails: "Always read context files before starting", "Keep code changes minimal and scoped to each task" — [apply SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-apply-change/SKILL.md)
- Propose skill steps: run `openspec context --json`, `openspec new change`, `openspec status --json`, then for each artifact `openspec instructions <artifact-id> --change "<name>" --json`, and "After creating each artifact, re-run `openspec status --change "<name>" --json`". Since 1.12.0, propose/ff are told to "inspect relevant project code, tests, and documentation before drafting artifacts" — [propose SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-propose/SKILL.md); [CHANGELOG 1.12.0](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- The proposal instruction already contains a token-saving pattern: "run `openspec list --specs`… then `openspec show "<spec-id>" --type spec --json --no-scenarios`… that returns a capability's purpose and requirement texts without pulling whole spec files into context". It then requires "read each relevant spec in full, including scenarios" before deciding coverage — [schema.yaml](https://unpkg.com/@fission-ai/openspec@2.1.1/schemas/spec-driven/schema.yaml)
- Skills are progressively disclosed: maintainer TabishB said "skills are progressively disclosed the context bloat is extremely minimal", since only name and description load up front — [issue #611](https://github.com/Fission-AI/OpenSpec/issues/611)
- The SKILL.md frontmatter has `allowed-tools: Bash(openspec:*)`, `compatibility: Requires openspec CLI.`, `metadata: {author: openspec, version: "1.0"}` — [apply SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-apply-change/SKILL.md)

### Inferences
- Rough baseline per feature (10 tasks, 4 review rounds), for one apply session per task (fresh context, as maintainers recommend): about 10 × [apply skill ~2.5k + status JSON + apply JSON (grows with the task list) + full proposal+specs+design+tasks (often 5–15k for a mid feature) + per-task re-run of apply JSON]. On top of that come review/verify passes (~4–5k skill + all artifacts + code search each). Skill + artifact re-reads alone could plausibly reach tens of thousands of tokens per task before any code is read. **This is an estimate, not a measurement.**
- The biggest levers are:
  1. Replace "read every context file" with a per-task slice (task text + linked requirements/scenarios from `show --json` + relevant design decisions).
  2. Replace per-task re-runs of `instructions apply --json` with a deterministic checkbox check done by the orchestrator.
  3. Replace the long generic skills with short task-specific prompts generated by the orchestrator.
  4. Trim `config.yaml` `context`.
  5. Shorten artifact instructions in a forked schema.
  6. Prompt caching: keep stable prefixes (skill text, project context) byte-identical across calls.
- The OpenSpec skills are LLM-agnostic Markdown, so a lean replacement can be dropped into `.agents/skills/<custom-name>/SKILL.md` without touching OpenSpec's files.

### Gaps
- No official token measurements exist. I found no OpenSpec doc or issue that quotes token counts for skills or instructions.
- Exact byte sizes of `instructions apply --json` output for a realistic change are not measured (requires running the CLI).

## 5. Per-task context, requirement IDs, traceability, and how /opsx:verify works

### Takeaway
OpenSpec has **no built-in per-task context, no stable requirement IDs, and no requirement→task→test traceability**. Requirements are identified by header **name** (`### Requirement: <name>`). Tasks have positional IDs like `1.2` with `sourcePath`/`line`. `/opsx:verify` (`openspec-verify-change`) is an **LLM-driven heuristic review**, not a deterministic check. It reads all artifacts, searches code by keywords, and reports CRITICAL/WARNING/SUGGESTION across Completeness, Correctness and Coherence. Stable IDs are an open proposal (#2167), and a community schema `spec-driven-ids` exists (#2157).

### Cited Findings
- Verify checks "three dimensions": Completeness ("All tasks done, all requirements implemented, scenarios covered"), Correctness ("Implementation matches spec intent, edge cases handled"), Coherence ("Design decisions reflected in code, patterns consistent"). It "Searches codebase for implementation evidence", reports CRITICAL/WARNING/SUGGESTION, and "Does not block archive, but surfaces issues" — [docs/commands.md#opsxverify](https://github.com/Fission-AI/OpenSpec/blob/main/docs/commands.md)
- Verify skill internals: it gets `openspec instructions apply --json` for `contextFiles`, `tasks` and `progress`, and reads "all available artifacts". Incomplete tasks are CRITICAL. A missing requirement implementation is CRITICAL ("Requirement not found"). For each scenario under ADDED/MODIFIED it should "Check if tests exist covering the scenario", otherwise WARNING "Scenario not covered". Heuristics: "Correctness: Use keyword search, file path analysis, reasonable inference - don't require perfect certainty"; "When uncertain, prefer SUGGESTION over WARNING, WARNING over CRITICAL". REMOVED requirements are checked against the baseline in the main spec (1.14.2/1.15.0 fixes) — [skills/openspec-verify-change/SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-verify-change/SKILL.md); [CHANGELOG](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- Skipped checks must be reported as "Not verified (<reason>)" and "Never score a skipped check as passing" (1.13.2 fix #1732) — [verify SKILL.md](https://github.com/Fission-AI/OpenSpec/blob/main/skills/openspec-verify-change/SKILL.md); [CHANGELOG 1.13.2](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- Archive matches MODIFIED/REMOVED/RENAMED by requirement `name` ("This is the name archive matches MODIFIED, REMOVED and RENAMED entries against") — [cli.md#openspec-show](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md)
- Issue #2167 (open, 2026-10-29) "Stable IDs for requirements, scenarios and decisions" proposes `### Requirement: [AUTH-3] Users sign in`, `#### Scenario: [AUTH-3.1] Correct password`, and decisions `### D1`, with "Brackets are required" and "Duplicate IDs are refused". The goal is to let tests, tasks and code link to specs. Coverage reports and two-way traceability are explicitly out of scope. The author reports agents kept IDs "in 264 of 265 runs". Implementation is split into #1979 (CLI) and #2134 (skills). No maintainer comment was visible — [issue #2167](https://github.com/Fission-AI/OpenSpec/issues/2167)
- Related open issues (titles only, not read in full): #2157 "Community schema: spec-driven-ids"; #2056 "Stable anchors for design decisions so other artifacts can link to them"; #900 "[Proposal] Optional test generation step bridging SDD and TDD"; #1652 "archive --yes proceeds on self-reported task status — should archive be able to require evidence?"; #783 "[Feature Request] Cross-artifact quality review between propose/ff and apply"; #1967 "Implementation and test details can end up in specs because they have nowhere else to go" — [GitHub issue search](https://github.com/Fission-AI/OpenSpec/issues?q=is%3Aissue+stable+ids)
- The task-level "verification" is only a text convention: since 1.10.0, generated tasks must "state how their completion can be verified" — [CHANGELOG 1.10.0 #1660](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- Apply returns per-task `sourcePath` and `line` (1.14.0) "so agents update the exact task, even when tasks span several files" — [CHANGELOG 1.14.0 #2018](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- The deterministic checks that do exist are `validate` (structure, scenarios, SHALL/MUST, lengths, archive merge preflight) and task checkbox counting. Archive "won't block on incomplete tasks, but will warn" — [cli.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/cli.md); [docs/commands.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/commands.md)

### Inferences
- For the hackathon's "100% requirement coverage by code and tests" constraint, OpenSpec offers no evidence-based gate. A token-saving layer should add a deterministic traceability matrix: requirement name (or a bracketed ID per #2167) → task IDs → test names → test results. This also lets most of verify run as a script, with the LLM used only for the residual semantic judgement.
- Bracketed IDs inside requirement/scenario headers (`[REQ-1]`) are already accepted by today's parser as part of the header name, since names are free text. They give stable grep-able keys for test names (e.g. `test_REQ_1_1_...`) without waiting for upstream support. The risk is that renames still match on the full name until #2167 lands.
- Because `tasks` has no field linking to requirements, the orchestrator must either ask the tasks-writer to add links in the text (e.g. `- [ ] 2.1 … (covers: REQ-3, REQ-4.1)`) via `rules.tasks` in config.yaml, or infer the mapping.

### Gaps
- I did not determine whether #1979/#2134 (stable-ID implementation) are merged into a release. They are not in the 2.1.1 changelog.
- Contents of community schema #2157 were not read.

## 6. Known issues and discussions on token usage, context bloat, large specs, and small models

### Takeaway
Maintainers acknowledge token cost mainly through workflow advice: "clear context between phases" and "high-reasoning models". There is no dedicated token-optimization feature. Community issues focus on duplicated text across artifacts and instructions, skill/command duplication, and context leakage. None quote measured token numbers.

### Cited Findings
- #1013 "Should a new chat/context be started when changing phases?". Maintainer clay-good: "Fair question, and the docs now take a position: yes, clearing between phases is fine, and usually better." The plan lives in files, so a fresh session resumes from the first unchecked task — [issue #1013](https://github.com/Fission-AI/OpenSpec/issues/1013)
- FAQ: "you can clear your context, start a fresh AI session, and pick up with `/opsx:apply`; it reads the artifacts and resumes from the first unchecked task"; "OpenSpec works best with high-reasoning models… Also keep your context window clean: clear it before implementation for best results." — [docs/faq.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/faq.md)

- #2215 (open, filed against 1.16.1) "Reduce cross-artifact duplication in task and template instructions". tasks.md repeated design decisions D3/D4 in one run, and the generic "fill in its sections" template guidance pushes redundant prose. Proposed fix: reference specs/design instead of restating them. No measured tokens — [issue #2215](https://github.com/Fission-AI/OpenSpec/issues/2215)
- Other relevant open or closed issues (titles only): #2139 "Spec guidance tells agents what to avoid, not how to keep a spec small and readable"; #257 "How to use OpenSpec when context exceeds limits or requirements change after implementation？" (closed 2025-10-30); #1771 "Feature Request: Automated end-to-end workflow (spec-kit style) with per-step model selection"; #1524 machine-level `context` in global config; #1651 "config.yaml context is loaded too late in the process" (closed); #846 "Built-in Context Persistence Support with Tracking Files" (closed); #802 "Spec Reuse: Auto-load archived specs or require explicit user context?"; #2209 "OpenSpec skills merging"; #2242 "Proposal: Extensible workflows and validation in OpenSpec"; #1910 "Add optional lifecycle hooks for sync and archive" — [GitHub issue search](https://github.com/Fission-AI/OpenSpec/issues?q=is%3Aissue+context)
- Small/local models: 1.13.2 changed continue commands so they "open with an instruction to follow the active OpenSpec workflow directly, so local models no longer try to call a tool named after it" (#1944) — [CHANGELOG 1.13.2](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- Guidance on large specs: the 500-character requirement limit (warning, fails `--strict`) and the "Consider splitting changes with more than 10 deltas" warning — [constants.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/validation/constants.ts)
- 1.14.1 changed the specs instruction to write each capability's spec file immediately, so "an interrupted run keeps the files it already wrote" — [CHANGELOG 1.14.1 #2037](https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md)
- Open issue #1910 requests lifecycle hooks for sync and archive, so no hook system exists yet — [issue search](https://github.com/Fission-AI/OpenSpec/issues/1910)

### Inferences
- There is no upstream "lean mode" or hook API. A token-saving layer must sit outside OpenSpec: as an orchestrator plus custom skills/schema, or as an opencode plugin or custom command layer.
- The maintainer-endorsed "fresh session per phase" saves conversation history but increases re-reads of skills and artifacts per session. That makes per-task slicing more valuable.

### Gaps
- No official benchmarks of OpenSpec token usage were found, and no data on performance with small models beyond the #1944 fix.

## 7. Brief comparison: spec-kit, Kiro, BMAD, Tessl, Taskmaster (artifact structure and token footprint)

### Takeaway
All of these tools persist plans as Markdown or JSON and re-read them per step. Taskmaster (per-task JSON records, `show <id>`) and BMAD (document sharding) have explicit mechanisms for loading only part of the plan. OpenSpec's distinctive feature is **delta specs** (change-scoped ADDED/MODIFIED/REMOVED) plus deterministic merge into living specs. Its per-task context defaults to "read everything". No source gives comparable token measurements.

### Cited Findings
- **GitHub spec-kit**: chat commands `/speckit.constitution`, `/speckit.specify`, `/speckit.clarify`, `/speckit.plan`, `/speckit.checklist`, `/speckit.tasks`, `/speckit.analyze`, `/speckit.implement`, `/speckit.converge`. Some agents use `$speckit-*` or `/skill:speckit-*`. Artifacts named: `spec.md`, `plan.md`, `tasks.md`, `checklists/requirements.md`. `.specify/feature.json` records the active feature dir — [spec-kit quickstart](https://github.com/github/spec-kit/blob/main/docs/quickstart.md); [spec-kit README](https://github.com/github/spec-kit)
- **Kiro**: "Every spec generates three files: `requirements.md` (or `bugfix.md`…), `design.md`, and `tasks.md`". When running all tasks, Kiro "builds a dependency graph from `tasks.md` and groups independent tasks into waves" — [kiro.dev/docs/specs](https://kiro.dev/docs/specs/). A third-party article says Kiro writes requirements in EARS notation — [dev.to (Torres Bermon)](https://dev.to/willtorber/spec-kit-vs-bmad-vs-openspec-choosing-an-sdd-framework-in-2026-d3j)
- **BMAD**: document sharding splits large markdown "based on level 2 headings" into a folder with `index.md` plus one file per section (example: a 50k-token `PRD.md` → `prd/` with ~12 files). Workflows load the whole doc if present, otherwise `<doc>/index.md`. Use it only if the tool/model "is failing to load and read all the documents" — [BMAD docs: shard large documents](https://docs.bmad-method.org/how-to/shard-large-documents/). The pipeline is Analyst → PM (PRD) → Architect → Scrum Master (stories) → Developer → QA, and "more agents means more tokens per cycle" (qualitative) — [dev.to](https://dev.to/willtorber/spec-kit-vs-bmad-vs-openspec-choosing-an-sdd-framework-in-2026-d3j)
- **Taskmaster (task-master-ai)**: `.taskmaster/tasks/tasks.json` holds tasks with `id` ("1.2"), `title`, `description`, `status`, `priority`, `dependencies`, `details`, `testStrategy` and `subtasks`. Commands: `next` (MCP `next_task`), `show <id>` (MCP `get_task`), `expand`, `set-status`, `update-subtask`. Its guidance says to use `task-master show <id>` "to pull in only the needed task instead of loading everything" and `/clear` between tasks (doc from v0.17.1, latest 0.43.1) — [task-master-ai AGENTS.md on unpkg](https://app.unpkg.com/task-master-ai@0.17.1/files/assets/AGENTS.md)
- **OpenSpec vs others (third-party)**: the article gives no token, context-size or per-task numbers for any framework, only qualitative claims. It still describes the outdated OpenSpec 0.x layout (`openspec/project.md`, `AGENTS.md`) — [dev.to](https://dev.to/willtorber/spec-kit-vs-bmad-vs-openspec-choosing-an-sdd-framework-in-2026-d3j)
- OpenSpec issue #1771 asks for "Automated end-to-end workflow (spec-kit style) with per-step model selection", which shows OpenSpec has no built-in automated pipeline runner — [issue #1771](https://github.com/Fission-AI/OpenSpec/issues/1771)

### Inferences
- Patterns worth porting onto OpenSpec:
  - Taskmaster-style per-task records: derive them from `instructions apply --json` plus `show --json`.
  - BMAD-style sharding: split design.md by `## Decisions` / `### D<n>` and serve only the referenced decisions.
  - Kiro-style task→requirement references and dependency waves.
  - spec-kit's `/speckit.analyze`-style cross-artifact consistency check: done deterministically, it would replace some LLM review iterations.
- OpenSpec's delta model already reduces review scope: only changed requirements appear in `openspec/changes/<id>/specs/`, so reviewers can be given deltas rather than full living specs.

### Gaps
- I did not verify with primary sources spec-kit's full per-feature layout (commonly cited as `specs/NNN-feature/{spec,plan,tasks,research,data-model,quickstart}.md`, `contracts/`, and `.specify/memory/constitution.md`), Kiro's exact paths (commonly `.kiro/specs/<name>/` and `.kiro/steering/*.md`), or Kiro's `_Requirements: x.y_` task references. Those are from general knowledge and should be checked before use.
- Tessl was not researched (no primary source fetched).
- No comparable token-footprint measurements exist across tools in the sources I found.
