# Контрольный процесс B0

Основание — §7 ТЗ и ADR-005. Исполнитель получает публичный текст фичи, закреплённую модель в формате `provider/model`, чистую рабочую копию и изолированный каталог конфигурации от `frugal run`. В каждом вызове opencode задан один и тот же идентификатор модели. Харнесс закрепляет его также для служебных вызовов и проверяет фактическую модель по данным измерителя.

1. В изолированном `XDG_CONFIG_HOME/openspec/config.json` задаются `profile: custom` и штатные workflows `propose, explore, apply, update, sync, archive, verify`. Команда `openspec init --tools opencode --scope project --no-animation` устанавливает семь skills в рабочую копию. Содержимое штатных skills берётся из закреплённого пакета OpenSpec.
2. Один сеанс `opencode run --command openspec-propose` получает имя change и полный исходный brief. Исполнитель проверяет появление proposal, design, tasks и непустого набора delta-spec. Следующий сеанс вызывает `openspec-apply-change` на весь список задач.
3. В новом сеансе `base-reviewer` проверяет полное изменение. В ответе остаются естественное объяснение, привязка замечаний к коду, пометки `BLOCKING:` / `NON-BLOCKING:` и итоговый вердикт. На открытое блокирующее замечание `base-fixer` получает полный текст ревью в новом сеансе. Затем изменение снова проходит полное ревью. Лимит — пять раундов.
4. `openspec-verify-change` выполняет штатную итоговую проверку. Если пятый раунд запросил исправление, исполнитель завершает fix и verify и сохраняет статус failed, поскольку подтверждение последним рецензентом отсутствует. Для успешного B0 нужны согласованные вердикты ревью и проверки, закрытые задачи, отдельные реальные ответы и неизменность проверяемого снимка. Факт успешного вызова хотя бы одного инструмента чтения, поиска, shell или дочерней задачи служит минимальной проверкой обращения к предмету ревью в новой сессии. Доказательства поведения и фактическое содержание ревью оцениваются независимым контуром WP-05.
5. После конвейера харнесс подключает независимую приёмку. Диагностика её тестов и гейтов исполнителю B0 недоступна.

Внутреннее имя операции `spec` объединяет четыре плановых артефакта одной сессии. Измеритель может уточнять атрибуцию по исходным событиям. Явное название сеанса одинаково используется в обоих плечах для учёта. Обычные инструменты и штатная компакция сохраняются. Настройки ролей помещаются в изолированный каталог opencode. Системные промпты и модель по ролям этими файлами не переопределяются.

## Доказательства одного выполнения

- `baseline.json` хранит хеш содержимого файлов `assets/agents/base/` и `assets/commands/base/`, отдельные хеши трёх применённых штатных skills, порядок стадий, номера раундов, идентификаторы сеансов и снимков.
- `b0/stages/*.md` содержит итоговое сообщение модели из последнего завершённого шага соответствующего сеанса. Полные исходные потоки, включая вызовы инструментов и ошибки, сохраняет харнесс.
- `b0/quality-review.json` связывает раунд, полное объяснение, транскрипт, дерево Git на входе и результат исправления. Для окончательной приёмки проверяется совпадение дерева последнего принятого ревью с деревом оцениваемого коммита.
- `b0/snapshots/<sha256>.json` перечисляет файлы на входе и выходе стадий. Исходное содержимое доступно в `b0/blobs/<sha256>`. Для символической ссылки сохраняется её цель как строка. Служебные каталоги .git, .venv, node_modules и кэши Python исключены. Канонический идентификатор дерева Git харнесс снимает с правилами индексации финального коммита.
- При незавершённом ответе, ошибке opencode или неоднозначном вердикте попытка завершается с ошибкой. Текст последнего доступного ответа и исходные события сохраняются. Новая попытка использует новый каталог.

## Воспроизведение технической проверки

Из корня чистого checkout выполнить:

```bash
npm ci
npm run build
node scripts/probe-baseline.mjs
```

Скрипт поднимает HTTP-сервер на 127.0.0.1 и создаёт одноразовую рабочую копию и каталоги конфигурации/данных вне проекта. Поставщик отвечает по заранее заданному сценарию. Настоящие opencode и OpenSpec разворачивают команды в штатные инструкции, пишут файлы инструментом write, перечитывают исходник и спецификацию для ревью и verify. В конце печатается путь к сырым потокам и снимкам. Статус этой проверки — технический smoke. Для приёмки WP-04 требуются два самостоятельных успешных B0 подряд на M-M и основной конкурсной фиче. Версию B0 закрепляют при первом калибровочном прогоне с записью в реестре решений.
