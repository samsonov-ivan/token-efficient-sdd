# Лимиты и подтверждение переводов

Расширить существующий API minibank. Клиенты создают счета через `POST /accounts` с полями `id`, `kind` (`personal` или `business`) и `balance`. Суммы целые, в копейках. Время берётся из внедряемых часов `create_app(db_path, clock=...)` в UTC. Примеры времени в ответах имеют вид `2026-11-21T13:00:00Z`. Существующие успешные запросы продолжают работать. Указанные ниже ошибки имеют точное тело `{"error":{"code":"..."}}`.

## REQ-LIM-01. Правила для типа отправителя

- SCN-LIM-01.1. `GET /limits/{kind}` возвращает 200 и объект из четырёх полей. Для personal значения `{"kind":"personal","per_transfer":10000,"daily":20000,"review_threshold":5000}`, для business — 50000, 100000, 25000 соответственно. `PUT /limits/{kind}` принимает три целых положительных числа с порядком `review_threshold <= per_transfer <= daily`, заменяет все три и возвращает обновлённый объект (200). Вместе с переводами изменения переживают пересоздание приложения на том же файле SQLite.
- SCN-LIM-01.2. Некорректная замена (пропуск, тип, порядок, ноль или отрицательное значение) даёт 422 `invalid_limits` и сохраняет старые значения. Неизвестный тип даёт 404 `unknown_kind` для чтения и замены.
- SCN-LIM-01.3. `POST /transfers` на сумму больше `per_transfer` отправителя даёт 409 `per_transfer_limit`. Равенство допустимо. Получатель не меняет выбор профиля.
- SCN-LIM-01.4. Сумма всех принятых исходящих переводов одного счёта за календарный день UTC, включая ожидающие, вместе с новым не должна превышать `daily`; иначе 409 `daily_limit`. Равенство допустимо, в 00:00 UTC начинается новый день. Ошибки и подтверждения расход второй раз не увеличивают.

## REQ-LIM-02. Запрещённые назначения

- SCN-LIM-02.1. Перевод на свой же счёт даёт 409 `self_transfer`.
- SCN-LIM-02.2. На закрытый счёт (`POST /accounts/{id}/close`) перевод даёт 409 `account_closed`. Обе ошибки сохраняют балансы, историю и суточный остаток.

## REQ-LIM-03. Повтор запроса

- SCN-LIM-03.1. Для `POST /transfers` необязательный заголовок `Idempotency-Key` (непустая строка) идентифицирует запрос отправителя. Повтор тех же destination и amount с тем же ключом возвращает исходные HTTP 201 и JSON даже после подтверждения или смены дня, без нового перевода.
- SCN-LIM-03.2. С тем же отправителем и ключом изменение destination или amount даёт 409 `idempotency_conflict`. У разных отправителей ключи независимы; без ключа каждый успешный запрос создаёт новый перевод.
- SCN-LIM-03.3. Неуспех не резервирует ключ. Одновременные повторы и перезапуск приложения не создают двойного списания или двух записей.

## REQ-LIM-04. Подтверждение

- SCN-LIM-04.1. Если сумма строго выше `review_threshold`, возвращается 201 с `status:"pending_review"`; деньги сразу списываются у отправителя, у получателя баланс пока прежний. При равенстве порогу сразу `completed` и обе стороны рассчитаны.
- SCN-LIM-04.2. `POST /transfers/{id}/confirm` без тела зачисляет сумму получателю ровно один раз, возвращает 200 с той же записью и статусом `completed`. `id`, `source`, `destination`, `amount` и `created_at` неизменны.
- SCN-LIM-04.3. Повтор подтверждения или подтверждение сразу завершённого перевода даёт 409 `already_completed`, неизвестный ID — 404 `transfer_not_found`.

## REQ-LIM-05. Фильтрация истории

- SCN-LIM-05.1. `GET /accounts/{id}/history` возвращает объект с `items` (записи переводов), `total` (до пагинации), `offset`, `limit`. По умолчанию offset=0, limit=50. Сортировка по целочисленному `id` убывает. История видна обеим сторонам.
- SCN-LIM-05.2. Необязательные `from` и `to` — даты YYYY-MM-DD в UTC, обе границы включаются. `type=incoming|outgoing` определяется относительно счёта, `status=completed|pending_review` — текущий статус. Все фильтры применяются совместно.
- SCN-LIM-05.3. `offset >= 0`, `1 <= limit <= 100`. Смещение после конца даёт пустую страницу с прежним total. Некорректные параметры, включая обратный период, дают 422 `invalid_history_query`.

## REQ-LIM-06. Аудит правил

- SCN-LIM-06.1. `GET /limits/{kind}/audit` возвращает 200 и `{"items":[...]}` в порядке внесения изменения. Изначально список пуст. Элемент содержит `before` и `after` (полные объекты правил включая kind) и `at` (время UTC).
- SCN-LIM-06.2. Записывать только успешные изменения значений. Ошибка или повтор той же конфигурации запись не добавляет.
- SCN-LIM-06.3. У типов клиентов отдельные журналы. Аудит обновляется атомарно с правилами, читается после пересоздания приложения на том же файле; неизвестный тип даёт 404 `unknown_kind`.

## Задачи приёмки

Довести до работающего результата 11 задач. (1) Схема хранения правил, (2) чтение и редактирование правил, (3) разовый лимит и запрет назначений, (4) суточный лимит, (5) сохранение ключей и проверка конфликтов, (6) конкурентный повтор и восстановление ответа, (7) ожидающие переводы, (8) атомарное подтверждение, (9) фильтры истории, (10) пагинация и ошибки, (11) аудит. Каждая задача получает публичный тест, отмеченный ID задачи и сценария.

Использовать идентификаторы задач `1.1`…`1.11` в указанном порядке и вышеприведённые ID требований и сценариев во всех артефактах.
