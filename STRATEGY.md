# Frugal SDD · стратегия на 27 часов

**Цель — показать, сколько сырых токенов экономится на одной принятой фиче и за счёт каких действий.** На защите жюри должно суметь выбрать требование, увидеть реализующий его код и зелёный тест, открыть модельный вызов до и после оптимизации и самостоятельно пересчитать итог. Самая ценная первая инвестиция — получить такую цепочку доказательств на стандартном OpenSpec + opencode. Следующее решение о расходе времени и квоты принимаем по этой трассе.

**Состояние на 21 ноября 2026, перед WP-00.** Из локальной папки Claude пришли ТЗ, исследование, 25 исходных гипотез и заготовки реестров. В единственной ветке GitHub `main` на коммите `271fb23` находились инженерное ТЗ Codex, обзор, три тематические заметки, инструкции и два PDF. В обоих источниках отсутствовали исполняемый CLI, плагин, стенды, журналы реальных пар и видеозапись. Все проценты в плане — цели или критерии принятия. Для старта из корня репозитория достаточно **«Делай»**. [Стартовый промпт](docs/START_PROMPT.md) · [исходный снимок GitHub](https://github.com/samsonov-ivan/token-efficient-sdd/tree/271fb238fd6d90e3b04b264efc2abb4a7cc1eb8a)

## 1. Что получит жюри

| Вес | Предмет проверки | Доказательство |
|---:|---|---|
| 35% | Экономия за полную фичу | Суммы base/opt, все пары и попытки, расход по стадиям, манифесты и воспроизводимый пересчёт |
| 25% | Сохранение качества | 100% требований и сценариев связаны с кодом и проходящими тестами, тест на каждую задачу, зелёная регрессия, согласованные specs/design/tasks, результаты закрытой приёмки и ревью |
| 15% | Разные классы LLM | Отдельные полные A/B внутри каждого класса, фактический идентификатор модели в каждом вызове, доля успешных запусков |
| 10% | Другой репозиторий | Установка того же дистрибутива на чистый сторонний проект, diff конфигурации, время настройки, полная приёмка его собственной фичи |
| 15% | Объяснение результата | Абсолютные токены и вклад стадий, однофакторные сравнения, примеры исчезнувших чтений и возникших дочитываний, сохранённые исходники |

Четыре результата сдачи — работающий прототип, живое по происхождению A/B на одной фиче, отчёт и воспроизводимая видеозапись. Для тестовой фичи в презентации указаны 8–12 задач и 3–5 итераций ревью. Сравниваем одинаковые требования, стадии, базовые инструменты, проверки, модель и провайдера. Из общей презентации для проекта используются только страницы 23–33. [Письменный кейс](case/token-efficient-sdd.pdf) · [слайды 29–32](docs/source/hackathon-presentations.pdf#page=29)

**Внутренние ориентиры.** Для большой модели минимум/цель/амбиция по RPT — 40/60/75%, для малой — 30/50/65%. Эффект выше амбиции принимается при тех же проверках. После E0 пересмотр целей оформляется решением с исходными данными. Процент экономии в баллы жюри самостоятельно не переводим. [ТЗ, §§1, 4](TZ.md)

## 2. Один продукт и одна контрольная фича

Реализуем **один CLI `frugal` и один плагин opencode** на TypeScript. Python нужен для статистики и отчёта. Из плана Claude берём стандартный B0, флаги, набор гипотез, пакеты WP-00…16 и серии E0…E10. Из плана Codex — контракт доказательств на финальном снимке, проверку полноты usage, восстановление после сбоя, отрицательные испытания и офлайн-воспроизведение. Предложенный там `sddbench` описывает тот же пользовательский путь. Работы W1–W7 распределены по WP в §5 ниже. Пары P1/P2/P3 служат демонстрациями основного стенда, другого класса модели и другого репо. Для закрытия соответствующей серии E требуется её полный объём по ТЗ. [ТЗ, §§6, 10, 16](TZ.md) · [разработка Codex, §§5, 7–10](SPEC.md) · [ADR-005](docs/DECISIONS.md)

- **Основная фича.** По умолчанию `minibank/add-transfer-limits` на Python/FastAPI + SQLite. Публичный контракт фиксирует лимиты, ошибочные переводы, идемпотентность, подтверждение, историю и аудит. Планируем 10–12 содержательных задач, включая межмодульные связи. Если к моменту фиксации WP-01 организатор предоставил фичу, используем её. Готовый резерв при непригодности стенда — `tickets export` с девятью обязательствами из SPEC §4. Решение, исходный SHA и эталон фиксируются до первого A. Запрещено менять фичу по увиденному проценту.
- **Проверка переносимости.** Заранее готовим два независимых checkout. Для JavaScript — `yocto-queue`, фича `peekLast()`, штатные AVA + tsd, включая несменившийся порядок элементов и публичный тип. Для Go — `google/uuid` v1.6.0, кандидат на изменение — строгий разбор канонической текстовой формы. В WP-01/13 подтвердить отсутствие требуемого публичного поведения, пригодность лицензии, чистую установку и зелёную исходную команду. В E5 сохранять хеш дистрибутива, команды, разницу конфигураций и результаты. Цели ТЗ — 0 правок ядра, ≤5 строк настройки и ≤5 минут установки. [Ревизия JavaScript](https://github.com/sindresorhus/yocto-queue/tree/72a8fa96a9d389765cdf2bb9c6daba8302fc375d) · [ревизия Go](https://github.com/google/uuid/tree/0f11ee6918f41a04c201eceeadf612a377bc7fbc)
- **Среда.** Основная линия — `opencode-ai@1.19.6`, E10 — адаптер V2 с отдельной A/B. OpenSpec `2.1.1` требует Node ≥22.20.0, резерв `1.17.0` требует ≥22.12.0. Закрепить точные рабочие версии, проектную область skills, загрузку плагина на обеих линиях и формат реального события до калибровки. Наблюдения исходного исследования Codex по V2 нельзя механически применять к V1. [ADR-001 и ADR-005](docs/DECISIONS.md) · [манифест OpenSpec 2.1.1](https://registry.npmjs.org/@fission-ai%2fopenspec/2.1.1)
- **Модели.** Codex 6.2 Sol и Astra разрабатывают и проверяют сам стенд. В измеряемом цикле выбор определяется реально доступными endpoint, поддержкой tool calling и наблюдаемым usage. Проверяем отдельно M-S, M-M и M-L. Для E4 добавляется четвёртая модель, всего минимум два провайдера. Название класса подтверждается данными поставщика. У каждого плеча все роли, включая фоновые LLM-вызовы, используют одну модель и провайдера пары. Выбор GigaChat оправдан при рабочем доступе и измерителе. Доступ к Codex для разработки сам по себе не подтверждает доступность модели для opencode.

В таблице указан начальный порядок пилотов. По E0 оцениваем долю стадии в RPT × долю повторов, которую реально можно убрать. Учитываем стоимость дополнительных запросов и исправлений. Полный набор кандидатов из обоих планов остаётся доступен за флагами. В итоговую конфигурацию попадают только прошедшие приёмку.

Чужие плагины сравниваем в E8 с соблюдением условий лицензий. [Каталог и карточки](docs/HYPOTHESES.md) · [исследование методов](RESEARCH.md) · [обзор аналогов и измерителя](reports/Источники%20по%20экономии%20токенов.md)

**Отбор.** Для каждой гипотезы сначала зафиксировать эффект, контрпример и лимит проверки. Дешёвый replay на сохранённом артефакте отсеивает потери данных. В E1 требуется одинаковый знак в ≥3 парах и медианная экономия ≥5% целевой стадии либо ≥2% всей фичи. Дополнительно — приёмка по §4.3, ≥2 пар на M-S, переносимость и выключаемый флаг. E2 проверяет комбинации. Для сильнейшего механизма снять и сравнение «полная конфигурация минус этот флаг». Провал качества исключает флаг. По исчерпании бюджета без результата перевести его в Parked и сохранить причину. [ТЗ, §§8, 15](TZ.md)

## 4. Когда сравнение пригодно для защиты

**Граница эксперимента.** Начинаем с одного неизменяемого brief и чистого SHA, заканчиваем на итоговых снимках двух независимо реализованных ветвей после verify и завершения фоновых запросов. Считаем токены обязательного предвычисления по конкретной фиче, родительских и дочерних сессий, ревью, исправлений, компакции и тарифицируемых повторов. Независимая оценка после конвейера имеет отдельную строку затрат. Если оценка направляет исполнителя, её расход входит в RPT. Каждый запуск получает свежий клон вне этого проекта, отдельные каталоги конфигурации и данных, изолированные логи и кэш. Исполняющий агент не может прочесть эталон, закрытые тесты или другое плечо даже по абсолютному пути. [ТЗ, §§7, 9, 10](TZ.md)

**Измеритель.** Сопоставляем поток `step_finish` с деревом сессий из хранилища opencode. На калибровке стремимся подтвердить итог независимым provider usage. Один вызов учитывается один раз. Нормализуем вход без кэша, чтение и запись кэша, видимый выход и reasoning в непересекающиеся поля. Повторный импорт даёт тот же итог. Конфликт двух записей с одним ID требует разбора. Известный расход без стадии входит в `other`, неизвестный расход отмечается явно. Для неоднозначной атрибуции S1–S4 допустима общая строка spec. При доступном логирующем прокси расхождение итогов должно быть <1%. Если прямой источник недоступен, сверить первичные события с экспортом, деревом сессий и итогом `opencode stats`, явно указать зависимость этих источников друг от друга. Неизвестный общий расход, необъяснённое расхождение или нулевой usage неподтверждённого вызова блокирует процент пары. [ТЗ, §§4.1, 10.2](TZ.md) · [контракты импорта и восстановления, §§5, 7](SPEC.md)

**Два уровня статистики.** В одной паре показываем A, B, экономию `100 × (1 − B/A)` при A > 0 и вклад каждой стадии в процентных пунктах `100 × (A_s − B_s)/A`. Сумма вкладов, включая накладные расходы, должна дать итог пары. Главный KPI серии E3 — `100 × (1 − median(B)/median(A))`. Рядом показываем все парные отношения, медиану, разброс, N, оценку неопределённости по §10.5, P_success и общий расход всех попыток на принятую фичу. Неудачи входят в журнал и знаменатель успешности. Неполные прогоны до таймаута получают отдельную строку. Первую оценку мощности по E0 сопровождаем явным предположением о разбросе парных различий, затем уточняем его на пилотах **до** итоговой серии.

**Качество.** Для каждого финального SHA сохраняем цепочку «публичное требование → сценарий → design → задача → символ в коде → assertion → идентификатор и результат теста». Общие правила ID вводятся в стартовый репозиторий обеих ветвей. Для потерянной метки применим проверяемый `trace --infer`. На этапе spec сверяем 100% ожидаемых поведений. Принимаем только полный зелёный набор без пропущенных обязательных тестов, полную матрицу и строгую плюс смысловую проверку OpenSpec. По серии сравниваем закрытые тесты, медиану раундов и успешность строго по §4.3. Независимый агент QA проверяет эталон на красной исходной базе для новой фичи, зелёной эталонной реализации и дефектных вариантах. Контрольные дефекты остаются вне конкурсных плеч. [ТЗ, §§4.3, 9](TZ.md) · [шесть отрицательных испытаний, §8](SPEC.md)

**Правило ревью.** В B0 действует естественная остановка по §7, максимум пять раундов. Номер и содержание каждого раунда сохраняются. До запуска регистрируем демонстрационную пару и условие для `D-review`. Если у выбранной пары фактически получилось 3–5 раундов в каждом плече, используем её в ролике. Иначе проводим отдельную полную пару с тремя заранее заданными проверками (контракт, граничные сценарии и тесты, итоговая согласованность), затем до двух повторов по замечаниям. Один регламент в обоих плечах. У этой пары свои ID и итог, у E3 — обычный B0. Бюджет на такой сценарий резервируем заранее. [ADR-005](docs/DECISIONS.md)

Зафиксированы SHA, состав серий, N и критерии исключения до финального запуска |
| 15–24 ч | WP-12/13/14 — независимые очереди E4/E5 и E3, как только их гейты пройдены, версия и входы заморожены. Заранее готовые профили и сторонние стенды используют тот же артефакт. E6/E8/E9/E10 планируются по свободной пропускной способности и правилам бюджета. WP-15 строит отчёт по мере появления данных. W5–W7 | Полные пары по квоте, отдельные статусы каждого эксперимента, подтверждение переносимости и сверка отчёта с сырыми событиями |
| Последние 3 ч | WP-15/16. Сформировать архив доказательств, итоговые графики, локальный дашборд, MP4 и инструкцию воспроизведения. Дополнительные серии завершаются только при наличии времени на повторную сборку и проверку комплекта | Другой агент в чистом checkout без вызова модели пересчитал отчёт, открыл видео, нашёл первичные данные по показанному требованию и проверил все четыре результата сдачи |

**Как планировать inference.** При доступных четырёх слотах распределить владельцев между координацией/интеграцией, измерителем/запуском, конвейером/плагином и стендом/независимой QA. Владелец реализации не принимает собственный эталон. При меньшем числе слотов совмещать независимые задачи последовательно. Worktree разработки и каталог измеряемого запуска — разные каталоги. Параллелить разные пары в пределах подтверждённого лимита endpoint. Внутри пары плечи соседствуют по времени, порядок фиксируется до запуска по §10.4. Отдельно лимитировать запросы и токены в минуту, исключать общие изменяемые кэши между прогонами.

После пилота посчитать доступные слоты каждого endpoint, фактическую стоимость и длительность обоих плеч, учесть 429 и время ожидания. Для предварительной оценки времени очереди использовать сумму плановых времен пар / измеренную параллельность, ограниченную также лимитами токенов. Для стоимости суммировать расходы по моделям и добавить запас 30% по §10.7. Резервировать время и квоту сначала на полные доказательства и повторную упаковку. При отставании переносить целые исследовательские серии. Для инженерного расширения остаются разработка флагов, тестирование негативных случаев и replay без дополнительных модельных вызовов. Неограниченная скорость написания кода особенно ценна именно здесь.

| Серия | Условия закрытия по ТЗ |
|---|---|
| E0 / E0-s | M-M и M-L по 5/минимум 3 обычных прогона, M-S 3/минимум 2. Технический smoke имеет отдельный ID |
| E1 / E2 / E7 | 5/минимум 3 на плечо или шаг. Для E7 сравнить долю обнаруженных подсаженных дефектов и задокументировать пропуски |
| E3 | Цель 10, минимум 8 полных сопоставимых пар на M-L. N фиксируется по калибровке. Одна качественная пара уже даёт A/B-демо с выводом об этом запуске |
| E4 / E5 | E4 — 5/минимум 3 пары на каждую из ≥4 моделей, ≥2 провайдера. E5 — 5/минимум 3 пары на каждом из двух сторонних репо. В манифестах E3 и E5 один SHA `frugal` |
| E6 / E8 / E9 / E10 | E6 — сильный B0′ на M-M и M-L, E8 — внешние аналоги, цель 5/минимум 3 по §10.3. E9 — S/M/L, E10 — отдельная линия V2, цель 3/минимум 2 |

При недостатке бюджета снижать N до минимума в порядке E8 → E6 → E9 → E10 → E1/E2 → E5 → E4 → E3. Если минимум недостижим, статус серии — «перенесена» или «незавершена», с фактическим объёмом и причиной. Даже при недоступной части матрицы упаковать состоявшиеся полные пары, отчёт и запись с точными границами выводов. При отсутствии реального endpoint продолжаются сборка, replay, QA и подготовка демо. До появления настоящих данных Ф0 и вывод об экономии остаются открытыми. [ТЗ, §§10.3–10.7, 16](TZ.md)

## 6. Приёмка и передача следующему агенту

Координатор после WP или сбоя обновляет `docs/STATE.md` (создаётся при первом запуске разработки). В записи нужны исходный дедлайн, последний принятый WP и SHA, незавершённые ветки и процессы, run ID, состояние квоты, проверенная команда и следующий открытый гейт. Каждый агент сдаёт локальный коммит, вход, команду проверки, выход и список ограничений. На возобновлении сначала сопоставить живые процессы, манифесты и уже потраченные токены. Незавершённая попытка сохраняется. Изменение B0 или кода финальной серии требует версионирования и повторения затронутых прогонов по ТЗ.

В релизе должны открываться:

1. CLI и плагин с установкой из чистого checkout, примером конфигурации и командами запуска обоих плеч.
2. Архив реальных данных из `bench/runs/<id>/` с манифестами, первичными событиями, нормализованным `calls.jsonl`, конечными diff, матрицами и отчётами тестов. Экспорт для жюри очищен от секретов, пути и идентификаторы пригодны для сверки.
3. Сгенерированные `report/REPORT.md` и `report/dashboard.html`. Все количественные результаты получены из архива. От таблицы можно дойти до конкретного события, включая строку с перерасходом или неудачей.
4. `report/demo.mp4`, внутренний ориентир 4–6 минут. Автоматически записать терминал или браузер с реальными run ID, показать исходный повтор, капсулу/дельту и открытие оригинала, одно требование с тестом, пересчёт итогов и перенос. Проверить декодирование, длительность и читаемость кадров. Для офлайн-показа указать, какая часть воспроизводит сохранённый прогон.

Первое действие в новом чате — выполнить стартовый промпт. В незакрытом пакете читаются его контракт и связанные проверки. Итоговая документация пополняется фактами по мере работы. [Промпт](docs/START_PROMPT.md) · [рабочие пакеты](TZ.md) · [реестр запусков](docs/EXPERIMENTS.md)
